PLAN — Multi-instance serve

dev board · task serve-multi-instance · Draft — awaiting plan_approved · spec →

Approach

Ship the MVP free-port fallback first — it fully satisfies the acceptance bar (two serves coexist) and is a small, contained change to the serve lifecycle. Treat .local stable URLs as a written recommendation; only implement if it turns out cheap. The core move: stop treating a busy preferred port as a fatal EADDRINUSE, and instead scan a bounded range for the first free port, then persist which port we bound so diagnose and the operator can find it.

Step-by-step work (MVP)

  1. Add a port-range picker. New helper in src/shared/process.ts (already the home of isPortInUse, isProcessAlive, identifyPortHolder) — e.g. findFreePort(preferred, rangeStart, rangeEnd) that tries preferred first then scans, returning the first free port or throwing a clear "no free port in 7475–7499" error. Prefer binding attempts over pre-probing to avoid a TOCTOU gap: attempt the bind and treat EADDRINUSE as "try next", rather than isPortInUse-then-bind (two processes could pass the probe and race).
  2. Introduce range constants. In src/http/server.ts alongside DEFAULT_PORT, add PORT_RANGE_START = 7475 and PORT_RANGE_END = 7499 (or export a single PORT_RANGE). Keeps the one source of truth the rest of the code imports.
  3. Rework the bind in serveCommand. In src/cli/commands/serve.ts (lines ~76–114), replace the single startHttpServer(app, port) + EADDRINUSE→throw block with a loop: for each candidate port, rebuild the allowedOrigins/allowedHosts/HttpConfig for that port (they're port-derived today, lines ~89–98), build the app, and startHttpServer; on EADDRINUSE continue to the next candidate; on the first success, keep it. Note: the app + allowlist must be rebuilt per attempt because the CORS/Host allowlist embeds the port. If SUBSTRATE_PORT_OVERRIDE is set, honor it exactly as today (no scan — tests pin an exact port), preserving the existing integer validation.
  4. Persist the chosen port. Extend the bookkeeping that today is just the PID file (paths(root).pid → .substrate/substrate.pid, currently writeFile(p.pid, String(process.pid), {flag:'wx'}) at serve.ts ~119). Pending Diego's answer on format (spec open question): recommended is a single gitignored runtime file .substrate/serve.json = { pid, port, started_at }, written with the same exclusive-create (wx) semantics after a successful bind so the race guard (Reviewer C-4) is preserved. Add serveRuntime path(s) to src/shared/paths.ts (SubstratePaths) so nobody hand-builds the path.
  5. Update cleanup paths. Every place that unlinks the PID file — the stale reclaim (serve.ts ~65), the shutdown handler (~149), and the beforeExit best-effort (unlinkSync, ~170) — must also clear the new port record (or, if we merge into one serve.json, just that one file). Keep the "PID dead ⇒ reclaim" logic keyed on the PID.
  6. Teach diagnose the real port. In src/cli/commands/diagnose.ts (lines ~41–47) it currently probes only DEFAULT_PORT. Change it to read the per-project runtime record: if present and its PID is alive, report "serving on port <port> (pid N)"; else probe the range and report which slots are in use, or "no server running here". This closes the "which port is this project on?" discovery gap.
  7. Update the startup log + help text. The logger.info at serve.ts ~133 already interpolates the chosen port — good. Update the header-comment flow description in serve.ts (§4 says "Bind Hono to 127.0.0.1:7475") and the CLI help line in src/cli/index.ts (~48, "default: http://localhost:7475") to mention the fallback range.

Recommendation

Defer .local for now; ship the MVP. A bare .local name (hosts or dnsmasq) does not solve the actual problem — routing to the right port — so it's cosmetic unless we also stand up an always-on reverse proxy that reads each project's persisted port and maps slug → 127.0.0.1:port. That proxy is a new supervised component (lifecycle, port-record watching, restart, staleness) — out of proportion to the MVP and to the acceptance bar. The MVP already makes multi-serve "just work"; combined with diagnose listing the port, discovery is solved without new infrastructure. Revisit the proxy as a separate task if shifting ports prove annoying in daily use; if so, dnsmasq + resolver (no per-project sudo) is the right name layer to pair with it, and the slug should derive from project_id to avoid basename(cwd) collisions.

Risks

  • TOCTOU on port selection. Probe-then-bind lets two racing serves pick the same port. Mitigation: drive selection by attempting the bind and catching EADDRINUSE to advance, not by pre-checking with isPortInUse.
  • Stale port record. A crash could leave a runtime file pointing at a port no longer served. Mitigation: gate reads on isProcessAlive(pid) (already used for PID reclaim) — a dead PID means the record is stale and should be ignored/reclaimed, same as the PID file today.
  • Format migration. If we fold PID+port into one serve.json, an in-flight old bare-substrate.pid from a previous binary could exist. Mitigation: on read, tolerate the legacy bare-PID file (treat as pid-only, port unknown); on write, always emit the new format. Low risk — the file is runtime-only and gitignored, never shared.
  • Discovery across many projects. With N serves on N ports, "which is which" is only answerable per-project via diagnose. Acceptable for MVP; a future substrate serve --list or the proxy would centralize it. Out of scope here.
  • Allowlist correctness. The origin/Host allowlist is port-derived; rebuilding it per bind attempt must use the port actually bound, or CORS/Host checks reject the browser. Covered by rebuilding HttpConfig inside the loop.
  • Range exhaustion. 25 concurrent serves is unlikely, but the error must name the range tried and suggest stopping an instance.

Test strategy

  • Unit: findFreePort — returns preferred when free; skips an occupied preferred to the next; throws a named error when the whole range is bound. Bind real ephemeral servers in the test to occupy slots (mirrors isPortInUse's own approach with node:net).
  • Integration / smoke: extend the pattern in tests/smoke/ui-seed-and-serve.ts — start one serve on the preferred port, then a second project's serve without SUBSTRATE_PORT_OVERRIDE (or with the override cleared) and assert it comes up on a different in-range port and its /health answers. Confirms the acceptance criterion (two coexisting serves, neither errors).
  • diagnose: extend src/cli/commands/diagnose.test.ts — with a live runtime record, diagnose reports the actual port; with a stale (dead-PID) record, it reports no server / probes the range.
  • Regression: single serve with 7475 free still binds 7475; SUBSTRATE_PORT_OVERRIDE still pins exactly and bypasses the scan (guards the existing test fixture); shutdown + stale reclaim remove both PID and port records.
  • Local gate: per CLAUDE.md, run build + tsc + lint + format + full tests locally (CI is billing-blocked) before setting tests_green.

Rollout

  • Backward compatible: the common single-serve case is unchanged (still 7475); the fallback only triggers on conflict. No config or schema migration — the runtime record is gitignored and regenerated each serve.
  • Ship MVP under this task on a feature branch off dev, PR into dev per the branching model; .local proxy, if pursued, is a follow-up task with its own spec/plan.
  • Docs: update README.md, the serve help line, and the serve.ts header comment in the same PR so the documented behavior matches. Version bump / release handled later via the release board.
