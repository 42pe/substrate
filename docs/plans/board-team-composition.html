PLAN — Data structures for per-board team composition

dev board · task 9a5af742 (board-team-composition) · Draft v4 — awaiting plan_approved · spec →

Approach

Introduce a project-level member registry plus a thin per-board team binding, and thread both through the places boards already flow: types → Zod parse → loader → integrity diagnostics → read-surface resolution (MCP + HTTP + UI). There is no engine work — team data is inert and groups is advisory (never gates a write or transition). The load stays successful: member↔board integrity problems are non-blocking warnings, not errors (Diego's v4 decision), because the whole member layer is optional and a project may keep its roster in prose.

The load path for member data is lenient. Unlike a malformed board file (which still fails the load via corruptBoardError), a malformed member file is warned-and-skipped, and a dangling member/groups reference or a duplicate is an advisory warning. None of these fail loadSubstrate, substrate validate, or a write. They route through the SAME advisory warning surface substrate validate already prints (⚠ …, exit 0) for policy smells — no new mechanism.

Beyond the core data structures, the build also (a) updates the default scaffolding so new projects get a real team, and (b) syncs the model docs. The migration of the two live boards and the default-scaffolding update are kept as separate stages: they solve different problems (fix the two existing boards vs. fix what NEW projects get).

The read surface is a single choke point: getBoardSubstrateHandler (src/mcp/tools/read/get-board-substrate.ts) backs both the MCP get_board_substrate tool and the HTTP GET /api/boards/:id route (src/http/routes/api/index.ts), which is what the UI's getBoard() fetches. It is where the registry JOIN happens — resolving member ids into full identities so every consumer sees resolved members (an unresolved member is surfaced, not dropped).

Target shape (on disk & over the wire)

// .substrate/members/oversight.json  (registry: identity, once)
{ "id": "oversight", "name": "Oversight",
  "full_description": "...", "traits": [...], "concerns": [...],
  "memory_dir": ".substrate/members/oversight/memory" }

// .substrate/boards/dev.json  (binding: assignment, per board; groups is advisory)
"team": [
  { "member": "oversight", "groups": ["spec", "review"] },
  { "member": "builder",   "groups": ["build"] }
]

// get_board_substrate result (resolved on read)
"team": [
  { "member": { "id": "oversight", "name": "Oversight", "full_description": "...",
                "traits": [...], "concerns": [...], "memory_dir": "..." },
    "groups": ["spec", "review"] }
]

How warnings are surfaced (grounding)

Today the load path is strict: loadSubstrate (src/substrate/loader.ts) throws corruptBoardError (src/substrate/corrupt.ts) on a bad board file, and substrate validate (src/cli/commands/validate.ts) treats a failed load as a non-zero exit. Separately, validate already has an advisory warning channel — it prints ⚠ … lines (e.g. a guard whose from_group === to_group) and still exits 0. This task extends that advisory channel to member/team integrity:

  • loadSubstrate gains a lightweight warnings accumulator (e.g. Substrate.warnings: string[], or a diagnostics list returned alongside) that member loading + integrity checks append to. It never throws for member issues.
  • substrate validate prints those warnings with the existing ⚠ format and stays exit 0 (a warning is advisory; only a failed load exits non-zero, and member issues no longer fail the load). substrate diagnose can likewise surface a count.
  • Member issues do not use corruptBoardError (that is the strict, load-failing path reserved for board files).

Step-by-step work

  1. Stage 1 — Types. In src/core/types.ts: add Member (id: string; name: string; full_description?: string; traits?: string[]; concerns?: string[]; memory_dir?: string) and TeamBinding (member: string; groups?: string[]); add optional team?: TeamBinding[] to Board and members: Member[] to Substrate (plus the warnings accumulator field if placed here). Doc-comment: descriptive + advisory (never gates); integrity issues are warnings; member = persona (distinct from the created_by_agent actor); memory_dir is a pointer only.
  2. Stage 2 — Zod schemas. In src/substrate/schemas.ts add MemberSchema (id/name required min(1); the rest optional) and TeamBindingSchema (member min(1); groups optional array). Add team: z.array(TeamBindingSchema).optional() to BoardSchema. Optional ⇒ a board with no team still parses. (These schemas are reused strictly by the template gate — Stage 8.)
  3. Stage 3 — Loader (registry, lenient). In src/substrate/loader.ts, read .substrate/members/*.json and populate Substrate.members. Add a membersDir helper to src/shared/paths.ts. Rules:
    • A missing members/ directory ⇒ members: [] (no error).
    • A member file that fails JSON.parse or MemberSchema.safeParse, or whose filename ≠ id, is skipped with a warning appended to the accumulator — it does NOT throw corruptBoardError and does NOT abort the load.
    • Members loaded before boards are validated, so the integrity pass (Stage 4) can resolve refs.
  4. Stage 4 — Integrity diagnostics (warnings, both paths). In src/substrate/validator.ts, add a member/team integrity pass that appends warnings instead of throwing:
    • Duplicate member id across the registry ⇒ warning.
    • Per board: a team[].member not present in the registry ⇒ warning; a groups id not a group on the board (archived OK) ⇒ warning; a duplicate member within one board's team ⇒ warning.
    • These run on both the load path and the write path (so update_board surfaces the same advisory), but as warnings — the earlier v2/v3 "dangling ref = error on both paths" framing is downgraded: it never fails validateBoardStructure or a write.
    • Wrinkle (carried from v1): the member-resolution check needs the set of registry member ids. Thread that set (and the warnings sink) into the shared board check so the write path produces the same warnings the load path does. A test asserts a dangling member yields a warning (not an error) on both paths.
    • Referential only, never enforcement. This pass must not make groups gate any write or move.
  5. Stage 5 — Read-surface resolution. In src/mcp/tools/read/get-board-substrate.ts: change BoardSubstrateResult.team to the resolved shape and map each binding, looking the member up in substrate.members. An unresolved member is surfaced (bare id + an unresolved marker), not dropped; empty/absent team ⇒ team: []. Add a tool-description line documenting the resolved team + the advisory groups join. No change in src/http/routes/api/index.ts (returns the handler verbatim).
  6. Stage 6 — UI type + render. In ui/src/lib/api.ts add the resolved team type to BoardSubstrate (import Member from @core/types). In ui/src/routes/BoardDetail.tsx add a "Team" Card to BoardDetailsDisclosure: iterate data.team, render member.name, its groups as assignment Badges resolved id→name, traits + concerns lines, full_description as a secondary/tooltip line; an unresolved member shows its id + muted "unresolved"; muted "No team declared" when empty. Reuse existing Card/Badge components.
  7. Stage 7 — Migrate the two live boards. Create one registry file per role under .substrate/members/ from the current ## Team prose (mapping below), add team bindings to dev.json and release.json, delete the ## Team section from each description (keep the process narrative), and bump each board's version. Reviewers ×2 is a single .substrate/members/reviewers.json referenced by both boards. Optionally create the empty memory_dir folders (with a .gitkeep / stub NOTES.md). Verify both boards load via get_board_substrate with zero integrity warnings after editing (drive from the main checkout only).
  8. Stage 8 — Default scaffolding (new projects; template gate STRICT). Distinct from Stage 7:
    • Add a team binding to the bundled web-delivery template (src/cli/templates/web-delivery.board.ts), members targeting its groups (Backlog / Spec / Plan / In Progress / Review / QA / Done), and author the matching default member registry files the template ships.
    • Extend substrate init (src/cli/commands/init.ts) to also write .substrate/members/*.json alongside the board file, inside the existing create/rollback try window (a partial init still rolls back cleanly). Add a membersDir mkdir.
    • The template validation stays strict. loadTemplateBoard / BoardSchema.parse (src/cli/templates/index.ts) fails loudly on a corrupt shipped board; validate the default member files through MemberSchema the same strict way at load/init time. This is a build-time invariant on Substrate's OWN artifacts — not the lenient runtime path for user-project member files. Keep the two clearly separate in code + comments.
    • Update the examples/web-delivery/.substrate/ source-of-truth copy (boards + new members/) so it stays parse-equal to the bundled template (tests/integration/example-substrate.test.ts).
    • Extend init.test.ts to assert the member files are written and the resulting substrate loads + validates with zero warnings.
  9. Stage 9 — Doc sync. Update the model docs to describe the structured member registry + advisory team binding (and the warning-not-error integrity contract) instead of free prose: skills/substrate/AUTHORING.md (board/policy model + a new members section), skills/substrate/SKILL.md, prd.md, README.md, docs/README.md. Risks & mitigations

  • An integrity warning accidentally made fatal. The whole point of v4 is that member issues never fail load/validate/writes. Mitigation: member loading + integrity never call corruptBoardError / throw; tests assert a dangling ref and a malformed member file both leave the load successful and validate at exit 0.
  • Lenient runtime vs. strict shipped defaults confusion. A reader might think the template gate was loosened. Mitigation: keep the strict loadTemplateBoard / MemberSchema gate for shipped defaults distinct in code + comments; a test proves a corrupt shipped default still fails, while a corrupt user-project member file only warns.
  • Advisory misread as a permission. Someone could later wire groups into a guard. Mitigation: neutral field name + documented semantics + a test that a write to any group succeeds regardless of team data; the integrity pass is referential only.
  • Warnings plumbing. loadSubstrate returns only Substrate today. Mitigation: add a small warnings accumulator to the load result and surface it through the existing validate/diagnose advisory output; do not overbuild a diagnostics framework.
  • Backward-compat regressions. Mitigation: team + registry optional; missing dir ⇒ []; tests parse a board with no team and a project with no registry.
  • Init scaffolding + rollback. Writing member files must not break the create/rollback window. Mitigation: write inside the existing try before the gitignore step; the rm(root) rollback removes the whole partial dir; an init test covers success + member presence.
  • Template ↔ example drift. Mitigation: update both; the parse-equal integration test guards it (extend to cover members).
  • Prose ↔ data drift. Mitigation: Stage 7 removes the ## Team prose; a test asserts neither migrated description contains a ## Team heading.
  • Memory pointer with no folder. Mitigation: inert string; Substrate never reads it, so a missing folder is not even a warning this task raises.
  • Scope creep (memory runtime / write tools). Mitigation: both explicit non-goals.
  • Unicode member names. "Reviewers ×2" has a non-ASCII ×. Mitigation: plain string end-to-end; a test round-trips it.

Test strategy

  • Registry parse. MemberSchema: a valid member parses; missing id/name fails the schema (used strictly by the template gate); optional fields absent OK.
  • Board-binding parse. TeamBindingSchema/BoardSchema: a valid team parses; a board with no team parses (optional); note the board schema itself still parses even if a binding will later warn.
  • Loader — lenient. A fixture with valid members/*.json populates Substrate.members; a project with no members/ loads with members: []; a malformed member file (bad JSON / missing fields / wrong types) is warned + skipped and the load still succeeds; filename≠id warns + skips.
  • Integrity — warnings, both paths, never fatal. A board whose team[].member is absent from the registry produces a WARNING and the board still loads; substrate validate prints the warning and exits 0. Same for an unknown groups id (archived group accepted, no warning) and for duplicate id/member. The write path (validateBoardStructure / update_board) produces the same warning and the write still succeeds.
  • Advisory / no enforcement. A task write / group move by any actor succeeds even when the actor is not a member targeting that group — team data never gates.
  • Strict shipped defaults. A deliberately corrupted web-delivery template board OR default member file makes loadTemplateBoard / MemberSchema.parse throw at build/test time — proving the template gate is not loosened even though user-project member files are lenient.
  • Read-join resolution. getBoardSubstrateHandler returns team with member identity JOINed in and the binding's groups; an unresolved member is surfaced (bare id + marker), not dropped; a board with no team ⇒ team: []. Assert the shared reviewers member resolves identically from both boards. Extend get-board-substrate.test.ts.
  • HTTP route. GET /api/boards/:id includes the resolved team (extend src/http/routes/api/api.test.ts).
  • UI render. BoardDetail.test.tsx: a team shows the Team card with member names, assignment (group-name) badges, traits, concerns; an unresolved member shows id + marker; an empty team shows the empty state without throwing.
  • Init scaffolding. init.test.ts: substrate init --template web-delivery writes the board and .substrate/members/*.json, and the result loads + validates with zero warnings. Parse-equal test covers template ↔ examples/web-delivery (members included).
  • Migration fidelity + prose removal. Load the real dev.json/release.json (or fixtures) and assert: each expected member resolves with the expected groups; reviewers is one shared file bound by both boards; descriptions contain no ## Team heading; both boards load with zero integrity warnings.
  • Inertness / no regression. Existing policy, guard, and whoami suites pass unchanged.
