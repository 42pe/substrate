PLAN — substrate activity

Approach

Build bottom-up along a path the codebase has already walked once. The pending-approval sprint shipped exactly this shape — one aggregate in src/operations/, consumed by an MCP tool, a CLI command and an HTTP route — and its header states the reason: “so the definition of ‘pending’ lives in exactly one place”. Follow it literally. That directory holds one file today; this adds the second.

Order is dictated by what everything else depends on:

  1. Repository — filters, ascending resume, count queries. Everything sits on this.
  2. Aggregate — src/operations/activity.ts: the substrate-as-code joins, the caps, the shape.
  3. MCP tool — the feature.
  4. HTTP — move the existing route onto the aggregate, additively.
  5. CLI — the printed half.
  6. Docs + cross-references.

No migration. The events are recorded, the indexes exist, the rowid is already the resume key. Everything here is reach, filter and shape — which is what makes the roadmap plan’s “cheap” sizing true, and what keeps BINARY_SCHEMA_VERSION at 2.

Four properties of the existing code that shape the work

  • The libsql client is single-threaded. src/storage/client.ts:95-97: “Do not issue concurrent statements on the same Client.” The counts view runs several queries — they must be sequential awaits, not Promise.all. board-columns.ts already does one query per column in a for loop; that is the accepted shape here.
  • Integer columns can come back as bigint. Every count must be coerced, as coerceId and countActiveTasksByGroup already do.
  • changes is opaque TEXT JSON. Counting policies_fired and reading move_blocked’s policy_id needs SQLite JSON1 (json_extract, json_each) — available in libsql, but with no precedent anywhere in this codebase. See the risk table for the fallback.
  • task_events has no board_id. Board scoping is the existing LEFT JOIN tasks, so a board filter necessarily drops events whose task row is gone. Documented (AC11), not worked around.

Step-by-step work

Step 1 — Repository: filters, ascending resume, watermark

src/storage/repositories/events.ts.

  • Add ProjectEventFilters { board_id?, event_types?, actor?, policy_id?, since?, until?, since_event_id? }.
  • Generalise listProjectEvents to take them. Keep the existing where: string[] + parallel args[] assembly — the filters AND together and compose with the cursor predicate that is already there.
  • Direction. since_event_id present ⇒ ORDER BY e.occurred_at ASC, e.id ASC with e.id > ?; absent ⇒ today’s DESC with today’s cursor tuple. Both cursor predicates already exist in this file (DESC at line 108, ASC at line 179 in listEvents) — reuse the forms, don’t invent a third.
  • board_id filters on t.board_id through the existing LEFT JOIN.
  • policy_id is one OR of two JSON predicates: 
    (
  (e.event_type = 'move_blocked' AND json_extract(e.changes, '$.policy_id') = ?)
  OR EXISTS (
    SELECT 1 FROM json_each(e.changes, '$.policies_fired') pf
    WHERE json_extract(pf.value, '$.policy_id') = ?
  )
)
    json_each over a missing path yields no rows, so events with no policies_fired key are simply non-matches — no null handling needed.
  • Watermark. One extra SELECT MAX(e.id) over the same FROM/WHERE, so it reflects the whole filtered window rather than the current page. Coerce the bigint. null when nothing matched.
  • Add listProjectEvents’ first direct unit tests — it has none today (only one integration assertion via /api/activity), and this step widens it considerably.

Step 2 — Repository: the count queries

Five queries, each returning rows the aggregate then joins and caps. All parameterized, all sequential.

Query Shape
countByEventType GROUP BY e.event_type
countByBoard GROUP BY t.board_id (via the LEFT JOIN)
countByActor GROUP BY e.actor_agent_name
countTransitions WHERE e.event_type='updated' AND json_extract(changes,'$.before.group_id') IS NOT NULL AND json_extract(changes,'$.before.group_id') <> json_extract(changes,'$.after.group_id'), grouped by board + before + after
countBlocks WHERE e.event_type='move_blocked', grouped by board + json_extract(changes,'$.policy_id') + from + to
countPolicyEngagements json_each(changes,'$.policies_fired') grouped by the entry’s policy_id + policy_type
countWrites Two numbers in one pass: total created|updated events, and how many have ≥1 agent_responsibility entry — EXISTS (SELECT 1 FROM json_each(...) WHERE json_extract(value,'$.policy_type')='agent_responsibility'). Counting per-write, not per-entry, is what makes AC9 hold.

Every one takes the same filter object and reuses the same WHERE builder, so a filter can never mean one thing in the events view and another in the counts view.

Step 3 — src/operations/activity.ts, the shared aggregate

  • Signature mirrors the precedent: activity(deps: Pick<ToolDeps, 'client' | 'loadSubstrate'>, input).
  • Substrate-as-code joins in TypeScript, following board-columns.ts: board_id → board_name, policy_id → policy_name + policy_type. A key with no match resolves to null, never dropped.
  • Caps applied here, not in SQL — sort desc by count, slice to counts_limit, set the truncated flag from rows.length > limit. One place, uniform across breakdowns.
  • by_event_type is driven off the TaskEventType union with ?? 0, not off the returned rows — the same “never trust SQL keys to be the full set” contract countActiveTasksByGroup’s consumer uses. So a type with zero events reads as 0, which is exactly the “dead stage / policy never engaged” signal.
  • responsibility_engagement_rate: total === 0 ? 0 : engaging / total. Guarding the zero case in the aggregate, not in three renderers.
  • A board_id that names no board throws not_found with the “use list_boards” hint — matching listPendingApprovals’ behaviour exactly.

Keep it dense; this string is in every agent’s context.

Step 5 — HTTP

  • getActivityHandler delegates to the aggregate. Parse the new filters with the existing strParam/listParam/intParam helpers, exactly as /api/tasks does.
  • Purely additive. No filters ⇒ byte-identical response to today, so the inspector’s Activity page is untouched (AC13). The UI is not rewired to use filters in this task.

Two renderers: an event table (time · board · type · actor · task) and a counts block (the breakdowns as small sections, truncated shown as a “+N more” line). The counts block prints responsibility_engagement_rate as a bare percentage with no colour and no judgement.

Risks & mitigations

Risk Mitigation
Context budget — the risk the plan says decides whether the feature is usable. A counts payload that grows with the window is the same failure as paging raw events. Caps live in the aggregate and apply to every breakdown; AC6 tests it directly by seeding an order of magnitude more events and asserting the serialized size barely moves. If the size is not bounded, the feature has failed its own test.
JSON1 has no precedent here. json_each/json_extract are used nowhere in the codebase; a libsql surprise would be found late. Spike it in Step 1, before writing the aggregate: one throwaway test that runs both against a seeded temp DB. If either misbehaves, the fallback is a bounded fetch of the filtered write events and counting in TypeScript — more memory, identical output, same public shape. Decide it once, early; do not discover it in Step 6.
Counts silently wrong. An aggregate that is subtly off is worse than none — it would be quoted in the dogfood journal as the PRD metric. Every count query gets a seeded unit test with a hand-computed expectation, including the adversarial cases: a write engaging two responsibility policies (counts once), an updated with no group change (no transition), an event whose task row is gone (no board), total === 0.
Resume loop drops or repeats an event when two events share a millisecond. The watermark is the rowid, not a timestamp — the exact reason the rowid exists. AC4 seeds tied occurred_at values explicitly.
Scope creep into an analysis engine. A rate invites a threshold; a blocks list invites “this gate is mis-authored”. Named as a hard non-goal in the spec, and enforced concretely: no colour, no comparison, no target anywhere in the CLI renderer or the payload. Reviewer (b) is briefed to look for it.
Overclaiming. “Supervision” / “audit trail” framing creeping into help text — the exact mistake the docs were corrected for once already. AC17 makes the honesty lines part of acceptance, not of taste.
Regressing the UI Activity page while refactoring its handler. AC13: no-filter response byte-identical. The existing integration test stays untouched and must still pass unmodified.
Filter semantics drifting between the events view and the counts view. One WHERE builder shared by all seven queries; a test asserts counts.window.events_matched equals the number of rows a fully-paged events read returns for the same filters.

Test strategy

Local gate only — CI is billing-blocked.

  • src/storage/repositories/events.test.ts — extend the existing 8 tests. listProjectEvents gets its first direct coverage: each filter alone; two combined (AND); policy_id matching both a move_blocked and a policies_fired write (AC3); ascending resume with a tied occurred_at yielding each event exactly once (AC4); watermark reflecting the window not the page (AC5); watermark null on no match. Then one test per count query with a hand-computed expectation, including every adversarial case in the risk table.
  • src/operations/activity.test.ts — new. The caps + truncated flags (AC7); policy_name: null for a policy absent from every board (AC10); by_event_type reporting 0 for an unseen type; responsibility_engagement_rate including the zero-writes case (AC9); not_found on an unknown board_id; the payload-size bound (AC6); events_matched agreeing with a fully-paged events read.
  • src/mcp/tools/read/activity.test.ts — new, following the colocated tool-test convention. Both views round-trip through wrapToolHandler; a bad event_types value returns a schema_violation envelope rather than a JSON-RPC error; the description mentions the honesty constraints (a cheap string assertion that keeps AC17 from rotting).
  • src/http/routes/api/api.test.ts — the existing /api/activity test passes unmodified (AC13), plus new cases for the filter params and a 400 on a bad page_size.
  • src/cli/commands/activity.test.ts — new, following pending-approval.test.ts: the pure renderer for both views; stripAnsi(color:true) === color:false; both empty states; --json parity with the aggregate; the resume footer; an unknown flag rejected.
  • Regression: substrate explain with the database file absent still succeeds (AC16), and BINARY_SCHEMA_VERSION is asserted still 2.
  • Manual, once, against the live dogfood DB: run substrate activity --counts --since <30 days ago> and read the responsibility-engagement rate. That number has never been computed in this project; getting it is the point of the feature, and eyeballing it once against the Activity page is the only end-to-end check that matters.

Local gate before tests_green: pnpm build, tsc --noEmit at the root and in ui/, pnpm lint, pnpm format:check, pnpm test.

Rollout

  1. Branch off dev. One PR into dev.
  2. Commit order follows the steps, with the JSON1 spike as its own throwaway commit that is dropped before review — the decision it produces goes in the PR body, not in the tree.
  3. Two independent reviewers, distinct lenses. Suggested split: (a) correctness — the SQL, the resume semantics, tied timestamps, bigint coercion, and whether the counts are actually right; (b) product/docs — is any of this a verdict engine in disguise, are the honesty constraints really in the shipped strings, is the reversal of the HTTP-only decision recorded.
  4. No migration, no schema version bump, so nothing to roll back in data. Older binaries read the same file unchanged.
  5. After merge, note in the dogfood journal what the first counts read said. The roadmap plan’s success signal is that a board changes because of it — and its kill signal is that nobody runs it twice.
