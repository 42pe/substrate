PLAN — Approval review surface in the inspector

dev board · task 9abed851 (approval-review-surface) · Draft v1 — awaiting plan_approved · spec →

Sequenced after dev task 69cd3660 — typed document references. Its GET /api/tasks/:id/documents is the contract this feature’s evidence panel reads.

Approach

Almost everything this needs is already built and already correct. The pending-approval aggregate, the per-task gate derivation, the comments and history reads, the approve/revoke pipeline including its stranded-task detection — all shipped. What is missing is one narrowly-scoped human write path over HTTP, and a place to stand while making the decision.

So the plan is deliberately back-to-front from how the feature reads. The refactor comes first, and it is the part that deserves the review attention:

  1. Extract the approval operation so the human_only assertion — the single check the whole feature’s safety rests on — exists once.
  2. Mount it on HTTP, with the origin tightening and without widening ApiDeps.
  3. Build the queue view (pure read, no affordance).
  4. Build the evidence panel, then attach the control below it.
  5. Throughput + docs.

Steps 1–2 are where a mistake would matter and where nothing is visible; steps 3–5 are where most of the diff is and where a mistake is obvious. Reviewing them in that order is the point of the ordering.

The three invariants to hold while building

  • ApiDeps gains nothing. It is Pick<ToolDeps, 'client' | 'config' | 'loadSubstrate'> precisely so HTTP cannot reach the substrate-write root. An approval writes a task row and reads the board from substrate-as-code — it needs neither root nor a file write. If a step seems to need root, the design has drifted; stop.
  • One human_only check. Not one per channel. This is why Step 1 exists.
  • No affordance without evidence. Any approve control outside the task-detail panel is a bug, not a convenience.

Step-by-step work

Step 1 — Extract src/operations/approval.ts

Pure refactor. No behaviour change; the existing CLI tests are the proof.

  • Two exported functions — setHumanField(deps, { taskId, field, value, actor, channel }) and clearHumanField(deps, { taskId, field, actor, channel }) — taking Pick<ToolDeps, 'client' | 'loadSubstrate'>, matching list-pending-approvals.ts’s narrowed-dep shape.
  • Move, unchanged: the board resolution, the human_only assertion and its exact error wording, validateFieldSchema, the OCC updateTask, the appendEvent, and (for clear) unapprove’s stranded-gate detection, returned as data rather than printed.
  • Add channel to the event changes. Backfill the CLI callers with 'cli' in this same step, so the field is never ambiguous by omission.
  • currentUser() moves here too — it is duplicated verbatim in both commands today.
  • approve.ts and unapprove.ts become argument parsing, a call, and printing. Their existing tests must pass unmodified; that is the refactor’s acceptance bar.

Step 2 — The HTTP write routes

  • POST /api/tasks/:id/approvals — body { field, value? }, value defaulting to true. DELETE /api/tasks/:id/approvals/:field.
  • Actor: human:${currentUser()}, from the serve process’s own OS user. Channel: 'inspector'.
  • Origin tightening. A small middleware applied to these two routes only: Origin must be present and allowlisted (the base middleware allows it absent). Do not change originAllowlist itself — the read surface’s curl/server-to-server behaviour is deliberate and other things depend on it.
  • Errors ride the existing errorHandler: not_found → 404, schema_violation → 4xx, version_mismatch → its mapped status. No new error shapes.
  • Replace the “Reads only — NO write route is ever registered” comment above registerApiRoutes with the sharpened two-channel property from the spec. Leaving a comment that the code contradicts is exactly the rot this project keeps correcting.
  • ui/src/lib/api.ts: apiPost/apiDelete helpers alongside apiGet, plus the two typed calls. Its header comment (“GET only — the server exposes no write routes”) needs the same correction.

Step 3 — The /approvals queue

  • ui/src/routes/Approvals.tsx + a route in main.tsx, reading GET /api/pending-approvals. No new endpoint, no new aggregate.
  • Grouped by board, mirroring the CLI table’s columns (title, short id, group → to_group, awaiting fields) so the two surfaces read the same.
  • Rows are links. Nothing else. AC8 asserts the absence of any button or checkbox in the rendered DOM — a negative test, deliberately, because this is the non-goal most likely to be “helpfully” re-added later.
  • A nav entry with a count, using the existing polling hook.

Step 4 — The evidence panel

  • A fourth tab in ui/src/routes/TaskDetail.tsx, shown when the task is pending or any human_only field is set. Computing that needs the board’s field_schema, so the route fetches GET /api/boards/:id as well — which also supplies the guard’s on_failure_message.
  • Compose the seven blocks in the spec’s order from existing reads plus GET /api/tasks/:id/documents. Read-only composition — no new server aggregate; every piece is a call the inspector already makes somewhere.
  • The documents block degrades cleanly: no document_refs field on the board ⇒ the block is absent, not an error state. That keeps the panel correct for any user’s board, not only ours.
  • Layout is load-bearing. The control sits at the bottom, after the evidence. No sticky footer, no button beside the title, no duplicate at the top. Scrolling past what you are approving is the mechanism.
  • Per awaiting field: an Approve button naming the field and the transition it unblocks. Per currently-set human_only field: a Revoke button, with the stranded warning rendered when the operation reports it.
  • On success, refetch the task and the approval state (the version has moved) and render the outcome plus “Next pending →”. On version_mismatch, render “this task changed — re-read before approving” with a refresh, never a retry-with-stale-version.

Step 5 — Throughput, then docs

  • “Next pending →” reads the queue and navigates to the next item’s Approval tab. Just navigation — it never approves, and there is no keyboard shortcut that could approve without a deliberate click.
  • README.md: the human channel is now “substrate approve or the inspector”; correct the line that says the UI is read-only, using the sharpened property rather than deleting the claim.
  • prd.md §6.13 / §6.17: the same restatement. This is the plan’s “conscious trade, not a slide” — write it down as one.
  • decisions.md: a dated entry recording the one deliberate UI write and the two-channel split.
  • CHANGELOG.md.
  • Not the B3 overclaim in README and the code comment — that is dev task d3f38afb, independent. Do not absorb it.

Risks & mitigations

Risk Mitigation
The human_only check diverges between channels — the failure that would quietly turn the flagship gate into theatre. Step 1 makes it physically single. AC1 asserts no second copy; the CLI tests passing unmodified prove the extraction was faithful.
The read-only slide. “While we’re here, let the UI edit a task.” The plan names this as the reason the property must be restated rather than waived. The property is written into the code comment, the README, the PRD and decisions.md. The operation is physically incapable of writing a non-human_only field, so the slide requires a deliberate, reviewable change — not a small addition.
Batch creeping back in as a “small convenience” — a button on the queue row, a select-all, a keyboard shortcut. AC8 is a negative DOM assertion, so re-adding it breaks a test with a name that explains why. Reviewer (b) is briefed on it specifically.
Evidence that isn’t evidence. A dead spec link rendered as a live one — precisely the failure the dependency on 69cd3660 exists to prevent. Dead references are marked and unlinked (AC10). If 69cd3660 slips, ship without the documents block; never fall back to spec_doc.
Widening ApiDeps because something “needs the root”. Named as an invariant above and asserted by AC3. Nothing in this feature writes a file.
Approving a stale task. The reviewer reads evidence, an agent writes, the approval lands on a task that has moved. OCC is already there. AC14 requires the conflict to surface as “re-read before approving”, never a silent retry — a retry would defeat the whole evidence premise.
Overclaiming the security property in the docs written in Step 5 — the mistake this project has already corrected once. The spec states the corrected B3 property; the doc edits quote it rather than paraphrasing. “Matches the CLI’s trust boundary”, never “airtight”.
Making approval easier without making it better. The plan’s own honest check: if the approval rate stays 100% forever, the gate is ceremony regardless of surface. Not a code risk and not fixable in code. Watch it in the dogfood journal — the signal the plan names is Diego occasionally declining or asking a question back.

Test strategy

Local gate only — CI is billing-blocked.

  • src/cli/commands/approve.test.ts, unapprove.test.ts — unmodified, passing after the extraction. The refactor’s acceptance bar.
  • src/operations/approval.test.ts — new. Sets and clears a human_only field; refuses a plain field, an undeclared field, and a human_only field from another board; stamps actor and channel; bumps the version; appends the event; reports stranded on a clear past a cleared gate; surfaces version_mismatch.
  • src/http/routes/api/api.test.ts — POST sets a field and returns the updated task; DELETE clears it; a non-human_only field is refused; unknown task 404s; absent and non-allowlisted Origin are refused on the write routes and accepted on the reads; a type-level assertion that ApiDeps still has no root.
  • Gate round-trip (integration) — a guarded move is blocked; POST the approval; check_transition now passes; DELETE it; check_transition blocks again (AC6). This is the test that proves the surface actually operates the gate rather than just writing a field.
  • B3 regression — with the write routes mounted, an agent’s update_task still refuses a human_only field and update_board still refuses to un-protect one. The new channel must not have opened an old door.
  • ui/src/routes/Approvals.test.tsx — new. Grouped rendering; the empty state; no button, checkbox or select-all in the DOM (AC8).
  • ui/src/routes/TaskDetail.test.tsx — the tab appears when pending and when a field is set, and is absent otherwise; all seven blocks render; a dead document reference is marked and not a link; a board with no document field renders no block; the control renders after the evidence in document order; the stranded warning shows on revoke; a version conflict renders the re-read state.
  • Manual, once, end to end: take a real pending approval, clear it from the browser, confirm the blocked agent’s next update_task succeeds, then substrate activity --actor human:$(whoami) and check the event says channel: inspector. That last check only exists if 847358dc has landed; otherwise read it via get_task_history.

Local gate before tests_green: pnpm build, tsc --noEmit at the root and in ui/, pnpm lint, pnpm format:check, pnpm test, plus the Playwright UI smoke if the tab is covered there.

Rollout

  1. After 69cd3660 merges to dev. Branch off dev at that point so GET /api/tasks/:id/documents exists to build against.
  2. Commit order follows the steps: refactor(approval): extract the human-only write to an operation → feat(http): approval write routes → feat(ui): pending-approvals queue → feat(ui): approval evidence panel → docs. The first commit should be reviewable as a pure no-op refactor.
  3. Two independent reviewers, distinct lenses. Suggested split: (a) correctness & security — the single human_only check, ApiDeps, origin handling, OCC under concurrent writes, and whether B3 still holds for agents; (b) product & docs — is the evidence genuinely above the control, did any batch affordance appear, is the read-only restatement honest in README and PRD, and is the B3 property described without overclaim.
  4. No migration and no data change. Reverting removes a route and a tab; every approval already made stays a normal task field.
  5. Dogfood signal from the plan: time from “agent reports blocked” to “gate cleared”, whether approvals stop arriving in clusters of five-plus, and — the honest one — whether Diego ever declines or asks a question back. If the rate stays 100%, the gate is ceremony and we should say so rather than admire the new surface.
