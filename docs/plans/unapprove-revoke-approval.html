PLAN — Unapprove / revoke a human approval

dev board · task a3c7177f (unapprove-revoke-approval) · Draft v1 — awaiting plan_approved · spec →

Approach

substrate unapprove is substrate approve run in reverse: the same resolve-board → human_only-guard → merge → OCC-write → stamp-event → print pipeline, with exactly one change in the middle — instead of merged = { ...custom_data, [field]: value } we do merged = { ...custom_data }; delete merged[field]. That is the identical deletion the MCP update_task handler already performs when it receives a null value (src/mcp/tools/write/update-task.ts lines 102–106): the repo's updateTask takes a fully-merged custom_data blob and writes JSON.stringify(merged) wholesale, so removing a key is purely a matter of handing it a blob without that key. No repository change, no new deletion primitive.

Correctness of the re-gate falls straight out of the operators (src/policy/operators.ts): exists is fieldValue !== null && fieldValue !== undefined — an absent key reads undefined → false → blocked; eq true is jsonEqual(undefined, true) → false → blocked. So deleting the key re-gates both guard shapes with no policy changes. The human_only guard is the same check approve.ts uses; because unapprove is CLI-only (no MCP tool), an agent has no path to it — symmetric with approve.

The one-line diff at the core

// approve.ts
const merged = { ...task.custom_data, [args.field]: value };

// unapprove.ts
const merged = { ...task.custom_data };
delete merged[args.field];

Step-by-step work

  1. New command src/cli/commands/unapprove.ts. Copy the skeleton of approve.ts (root/existence check, sink config, DB open, loadSubstrate, withTransaction, currentUser() → human:<user>). Signature unapproveCommand(cwd, { taskId, field }) — no value.
  2. Human-only guard (reused, first). Resolve board.field_schema.task[field]; if not human_only === true, throw SubstrateError.schemaViolation with unapprove-flavored wording. This runs before any idempotency check so wrong/typo'd fields always error.
  3. Idempotent no-op. After the guard, if !(field in task.custom_data), write the "Nothing to revoke" line to stdout and return from inside the command (no transaction, no version bump, no event). Mirrors the repo's archive/unarchive idempotency (a no-op emits nothing).
  4. Delete + OCC write. Else build merged = { ...task.custom_data }; delete merged[field], call validateFieldSchema({ field_schema, merged_custom_data: merged, touched_keys: [field] }) (an absent key is always allowed — field-validator.ts skips undefined), then updateTask(tx, taskId, task.version, { custom_data: merged }, now).
  5. Event stamping. appendEvent with event_type: 'updated', changes.before.custom_data = task.custom_data, changes.after.custom_data = merged, and actor_agent_name: 'human:<user>' — byte-for-byte symmetric with approve's event.
  6. Confirmation output. Revoked: cleared <field> (was <JSON old value>) on task <id> (as <actor>, version <n>).
  7. Stranded warning (conditional). Add a small helper that finds active transition_guard policies on the task's board whose require tree references the revoked field and whose to_group === task.group_id. If any match, print a Warning: second line (see spec). Reuse parseGuardDefinition, collectLeaves, and taskFieldName from src/policy/pending-approval.ts — export the two currently-private helpers (collectLeaves, taskFieldName) or move them to a shared module so both call sites use one implementation. Scope: direct to_group match only (no multi-hop reachability).
  8. Flag plumbing — args. In src/cli/args.ts, add unapprove: new Set() to the allowlist (mirrors approve), so rejectUnknownFlags accepts the command and rejects stray flags.
  9. Dispatch — index. In src/cli/index.ts, add case 'unapprove' mirroring case 'approve': parse [taskId, field] = rest, print a usage line if either is missing (Usage: substrate unapprove <task_id> <field>), then await unapproveCommand(cwd, { taskId, field }). Import unapproveCommand.
  10. HELP text. Add a substrate unapprove <task_id> <field> line to the HELP block, right after the approve entry, describing it as the revoke channel that clears a human-only field so the gate re-blocks.
  11. Tests. New src/cli/commands/unapprove.test.ts (details below), plus an args assertion that unapprove accepts no unknown flags.

Risks & mitigations

  • Fabricating a non-existent move command. There is no substrate move CLI. Mitigation: the stranded warning references the board (web UI) / an agent's update_task, never a fake CLI verb. Covered by a test that asserts the warning text does not contain substrate move.
  • Over-broad stranded detection. True "past the gate" across multiple hops needs group ordering and reachability — over-engineering for v1. Mitigation: detect only the direct case (current group === a requiring guard's to_group); document multi-hop as a known limitation. False negatives just omit a warning; they never move or block anything.
  • Idempotent no-op masking a typo. A mistyped field could look like "already unset". Mitigation: the human_only check runs first, so any field that is not a declared human-only gate field errors with schema_violation; only a genuine, declared gate field that is currently unset becomes a quiet no-op.
  • Deleting a field read by more than one guard. Deletion clears exactly the named field; if the same approval field gates several transitions, all of them re-block — which is the intended semantics of revoking that approval. Noted, not mitigated.
  • Exporting internal policy helpers widens surface. Mitigation: prefer a small shared field-refs.ts extraction with its own unit test, or a minimal named export; the derivation keeps calling the same code so "pending" and "stranded" never diverge.
  • OCC / concurrency. The delete goes through the same version-checked updateTask as every other write, inside one withTransaction; a concurrent writer yields version_mismatch, not a lost update. No new concurrency surface.

Test strategy

Mirror src/cli/commands/approve.test.ts: same tmp-dir + board fixture harness, driving the real command against a migrated SQLite DB and asserting task state, events, and check_transition. The board fixture already carries a plan_approved human_only boolean and an exists gate; extend it with a second guard using { op: eq, value: true } and a done/target group for the stranded case.

  • Re-block, exists guard (required). approve → assert check_transition allowed; unapprove → assert check_transition blocked again; assert the field is absent from custom_data (not false).
  • Re-block, eq true guard (required). Same round-trip against a guard whose leaf is { op: eq, value: true } — deletion makes eq true evaluate false and the gate blocks.
  • Human actor + event. After unapprove, the latest updated event has actor_agent_name matching /^human:/, before.custom_data contains the field, after.custom_data does not.
  • Version bump + confirmation. Version increments by 1; captured stdout contains the old value, "cleared", and the new version.
  • Non-human_only field refused. unapprove(..., { field: 'severity' }) rejects with code: 'schema_violation' and leaves state unchanged.
  • Idempotent no-op. Calling unapprove on plan_approved when it was never set exits 0, prints "Nothing to revoke", and leaves version + event count unchanged (assert no new updated event).
  • Not-found. A missing task id rejects with a SubstrateError (not_found).
  • Stranded warning, no move. Move the task to the gate's to_group (via updateTask after approval), then unapprove: assert stdout contains the Warning: line, the warning does not contain substrate move, and the task's group_id is unchanged.
  • Full round-trip. approve → allowed → unapprove → blocked → approve → allowed, proving exact symmetry.
  • Args. Extend the args test so unapprove is a known command and an unknown flag on it exits non-zero.
  • Field-refs helper (if extracted). Unit-test that collectLeaves / taskFieldName map a nested all_of/any_of require tree to the expected field names.
