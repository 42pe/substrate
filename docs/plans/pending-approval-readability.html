PLAN — Pending-approval readability

dev board · task c607b04e (pending-approval-readability) · Draft — awaiting plan_approved · spec →

Approach

Keep the derivation untouched — the CLI already fetches the shared aggregate via listPendingApprovals({ client, loadSubstrate }) (src/operations/list-pending-approvals.ts), which is also what the list_pending_approvals MCP tool and the HTTP route return. This task rewrites only the rendering half of src/cli/commands/pending-approval.ts, plus a small flag addition.

The core move is to extract rendering into a pure function — renderPendingApprovals(result, { color }) returning a string — so the command becomes "fetch → decide color → render → write", and the table/color logic is unit-testable without stubbing process.stdout or a TTY. Color is produced by a new tiny ANSI helper (no dependency). Alignment math measures visible width so escapes never throw off the columns: build plain cells, compute column widths and truncate on the plain text, pad, then wrap the padded cell in color. --json short-circuits before any rendering and prints JSON.stringify(result, null, 2) for exact parity with the MCP tool.

Step-by-step work

  1. Add a tiny ANSI helper. New module src/cli/color.ts (CLI-local; the only consumer). Exports: a small set of wrappers (bold, dim, cyan/yellow, etc.) each taking (s, enabled) and returning s unchanged when enabled === false; a stripAnsi(s) (used by tests + width math); and colorEnabled() that returns process.stdout.isTTY === true && !process.env.NO_COLOR. Escapes are raw string literals (\x1b[1m … \x1b[0m) — no dependency.
  2. Add a text/width helper. Small pure helpers (colocate in color.ts or a sibling src/cli/table.ts): visibleWidth(s) = stripAnsi(s).length; truncate(s, max) = ellipsis-clamp on the plain string; padEnd(s, width) that pads by visible width. A minimal column-layout function that, given rows of plain cells + a terminal width, computes per-column widths and shrinks the flexible Task column first (floor ~24, then ellipsis) so no row exceeds the width.
  3. Extract the renderer. In pending-approval.ts, add renderPendingApprovals(result: PendingApprovalsResult, opts: { color: boolean; columns?: number }): string. It reproduces today's grouping (build the Map<board_id, items[]>), emits the count line, then per board a bold header and the aligned rows. Cell contents: Task = truncated title + (shortId); Move = ${it.group_id} → ${it.gate.to_group}; Awaiting = it.awaiting_fields.join(', '); Approve = the first field's command (with a note/extra rows if multiple — keep one approve line per awaiting field, matching today's guarantee). Short id = first 8 chars of task_id (or full if already short).
  4. Rewire the command. pendingApprovalCommand(cwd, opts: { json?: boolean }): keep the .substrate existence check, sink config, DB open, and listPendingApprovals call. Then: if opts.json → process.stdout.write(JSON.stringify(result, null, 2) + '\n') and return (works for the empty case too). Else if result.count === 0 → today's empty-state line. Else → process.stdout.write(renderPendingApprovals(result, { color: colorEnabled(), columns: process.stdout.columns })). Keep the client.close() in finally.
  5. Flag plumbing — args. In src/cli/args.ts, change the 'pending-approval' entry from new Set() to new Set(['--json']) so rejectUnknownFlags accepts it (and still rejects anything else).
  6. Flag plumbing — dispatch. In src/cli/index.ts, the case 'pending-approval': compute const json = rest.includes('--json') before/after rejectUnknownFlags('pending-approval', rest), then await pendingApprovalCommand(cwd, { json }). (Mirrors how logs reads --errors via rest.includes.)
  7. HELP text. Update the pending-approval line in the HELP block of index.ts to note the aligned-table output and [--json].
  8. Tests. Extend src/cli/commands/pending-approval.test.ts (details below) and, if color.ts grows non-trivial helpers, add src/cli/color.test.ts.
  9. Local gate. Run tsc + lint + format + full test suite locally (CI is billing-blocked — validate locally) before setting tests_green.

Risks

  • Alignment vs. color escapes. Padding by raw string length would be thrown off by escape bytes. Mitigation: compute widths/truncation on plain cells, colorize only after padding; visibleWidth uses stripAnsi. A test strips ANSI and re-checks alignment.
  • Wide-character / unicode titles. .length counts code units, not display columns; a CJK/emoji title could misalign. Accepted for v1 (matches the codebase's plain-ASCII assumptions elsewhere); note it, don't pull in a grapheme library (would violate "no new dependency").
  • Unknown terminal width. process.stdout.columns is undefined when piped. Mitigation: fall back to 80 (open question 2); truncation still bounded and deterministic for tests.
  • Breaking scripts that scrape the old prose. The list format changes. Mitigation: --json is the stable machine surface going forward; the human format is explicitly not a contract.
  • Multiple awaiting fields per task. Keep one approve command per field (today's guarantee) so the table may carry a stacked/secondary line for multi-field tasks — verify the row stays aligned. Most gates are single-field.
  • Test flakiness from real TTY. Vitest runs non-TTY, so colorEnabled() is naturally false; color-on tests call the pure renderer with { color: true } rather than faking a TTY.

Test strategy

Prefer testing the pure renderer directly (no stdout/TTY mocking) plus a couple of command-level integration tests that keep the existing process.stdout.write spy harness in pending-approval.test.ts.

  • Layout. With ≥2 pending tasks across 2 boards, renderPendingApprovals(result, { color: false }) contains the count line, both board headers, and each row; assert the column header row and a data row share the same column start offsets (alignment).
  • Plain / NO_COLOR is escape-free (required). Assert renderPendingApprovals(result, { color: false }) contains no \x1b[. Plus a command-level test that sets process.env.NO_COLOR='1' (restored in afterEach) and asserts the captured stdout has no escape bytes — proving the TTY gate wires through colorEnabled().
  • Color mode. renderPendingApprovals(result, { color: true }) contains escapes, and stripAnsi(colored) deep-equals the { color: false } render — color adds nothing the plain text loses.
  • --json parity (required). Run the command with { json: true }; JSON.parse the captured stdout and assert it deep-equals the value returned by listPendingApprovals for the same fixture (same shape as the MCP tool). Assert the JSON output contains no escape bytes even when forced color: true upstream (JSON never colorizes).
  • --json empty state. With no pending tasks, --json yields valid JSON with count: 0, items: []; without --json, the existing "No tasks pending human approval" line is preserved.
  • Runnable command cell. Assert a row's Approve cell equals exactly substrate approve <task_id> <field> for the fixture (verbatim, one per awaiting field) — the copy-paste guarantee.
  • Truncation. A very long title at a narrow columns is clamped with an ellipsis and the short id stays intact; no rendered line exceeds the width.
  • Flag rejection. Keep/extend an args.ts test that --json is accepted for pending-approval and an unknown flag still exits non-zero.
