PLAN — Skill/binary sync

dev board · task aa08a050 · Draft — awaiting plan_approved · spec →

Approach

Three coupled pieces, smallest-blast-radius first: (1) package the skill so a source of truth ships with the binary; (2) a command (substrate install-skill, pending naming) that copies the packaged skill into ~/.claude/skills/substrate, stamps a version, and offers a read-only --check drift report; (3) surface drift in diagnose and wire the refresh into the release ritual (docs + release board).

The one genuinely new capability is runtime resolution of the binary's own install path. Today nothing in src/ uses import.meta.url/fileURLToPath — bundled templates are compiled to JS board modules (src/cli/templates/*.board.ts), never read from disk. Since the skill is markdown files (not code), it must be resolved from the package on disk. Recommended: add skills to package.json files and resolve <pkgRoot>/skills/substrate from the command module via fileURLToPath(import.meta.url). The compiled command sits at dist/server/cli/commands/install-skill.js, so the package root is four levels up (../../../../). This keeps skills/ as the single authored source and avoids duplicating it into dist/. (Alternative, if we'd rather not walk relative levels: copy skills/ into dist/ in scripts/post-build.mjs and resolve relative to dist/server/ — rejected as v1 default because it duplicates the tree and complicates the files story.)

Step-by-step work

  • 1. Package the skill. Add "skills" to the files array in package.json. Verify with pnpm pack + tar -tzf that skills/substrate/SKILL.md and AUTHORING.md are in the tarball.
  • 2. Stamp helper (core). Add a small module (e.g. src/core/skill.ts) exporting: the install target path ~/.claude/skills/substrate (via os.homedir()); a packagedSkillDir() that resolves <pkgRoot>/skills/substrate from import.meta.url; readInstalledStamp() / writeStamp(version); and a compareSkill() returning { installed, expected: BINARY_VERSION, state: 'ok'|'drift'|'missing' }. Stamp mechanism per Diego's answer (recommend a sibling .version file so SKILL.md stays pristine).
  • 3. New command. Add src/cli/commands/install-skill.ts exporting installSkillCommand(opts: { check?: boolean }). Default: recursively copy packagedSkillDir() → target (create parents), write the stamp, print "installed/updated to vX.Y.Z" or "already current" (idempotent — compare first, skip write when identical). --check: call compareSkill(), print the state, set process.exitCode = 1 on drift/missing, write nothing.
  • 4. Dispatch + flags + help. In src/cli/index.ts: import the command, add a case 'install-skill' (and/or 'update') to the switch, add a HELP block line. In src/cli/args.ts: add 'install-skill': new Set(['--check']) to ALLOWED_FLAGS_BY_COMMAND. The command takes no positional, so read --check via rest.includes('--check') then rejectUnknownFlags.
  • 5. Diagnose probe. In src/cli/commands/diagnose.ts, add a wrapped probe under a new "Skill:" section that calls compareSkill() and emits ok()/bad() — bad() already increments problems and flips the exit code, matching the existing pattern. Decide with Diego whether drift is a hard ✗ (counts as a problem) or an advisory ok() line like the historical-errors block.
  • 6. (Optional) whoami hint. If we want agents to notice mid-session, add a conditional hint string in src/mcp/tools/read/whoami.ts (hints[]) when compareSkill().state !== 'ok'. Lower priority; whoami is read-hot, so keep the check cheap/cached.
  • 7. Release wiring. Update RELEASING.md "After a release" to add the skill-refresh command after the binary reinstall, and fix the files list in the "Publishing to npm" note (add skills). Update .substrate/boards/release.json: the rel-gate-tagged policy on_failure_message and the rel-versioning/Released guidance to say "reinstall the binary and refresh the skill (substrate install-skill)". (The board description already lists "global reinstall + skill refresh" as a Release-Engineer concern and "installed-skill vs binary drift" as a Doc-Auditor concern — the gate message just lags the intent.)
  • 8. CHANGELOG. Add an Added bullet under ## [Unreleased] in CHANGELOG.md (user-facing: the new command + drift check).

Risks

  • Install-path resolution is new territory. Walking ../../../../ from dist/server/cli/commands/ is brittle if the build layout changes. Mitigate: centralize in src/core/skill.ts, add a test that asserts the resolved packagedSkillDir() actually contains SKILL.md so a layout change fails loudly.
  • Writing into ~/.claude. The command touches the user's home config. Keep it explicit (no postinstall), print the exact target path before/after writing, and never delete unrelated files (copy/overwrite only the substrate subdir).
  • Two version-of-truth surfaces. A sibling .version file can be deleted independently of SKILL.md; a frontmatter field mutates authored content. Whichever Diego picks, --check must treat "stamp missing" as drift, not a crash.
  • Stale-stamp false-negative. If we stamp only on install but the packaged content changed without a version bump, --check could report "ok" while content differs. Mitigate: compareSkill() can also hash the content, or we rely on the invariant that skill changes ride a release (which bumps BINARY_VERSION). Decide during review.
  • Package bloat / accidental excludes. Adding skills to files must not sweep in AUTHORING.md if we decide it shouldn't ship (currently fine to ship both). Verify the tarball contents.
  • CI is billing-blocked (see memory: CI Actions billing limit) — all gating is local; the plan's test strategy must be runnable locally end-to-end.

Test strategy

  • Unit — compareSkill(): returns ok when stamp == BINARY_VERSION, drift when different, missing when the target dir/stamp is absent (use a temp HOME).
  • Unit — command copy: against a temp home dir, first run creates the tree + stamp; second run is a no-op ("already current"); a stale stamp is repaired to BINARY_VERSION and content re-synced. Assert copied files are byte-identical to packagedSkillDir().
  • Unit — --check exit codes: 0 on match, non-zero on drift/missing, and asserts no filesystem write occurred.
  • Unit — args: extend src/cli/args.test.ts — --check is accepted for install-skill, any other flag is rejected.
  • Packaging: a test (or a documented pnpm pack + tar -tzf check) asserting skills/substrate/SKILL.md is in the tarball.
  • Diagnose: if a diagnose test exists, assert the new "Skill:" line appears and that a drifted skill influences the exit code per the chosen convention.
  • Local full gate before tests_green: pnpm build && tsc && pnpm lint && pnpm format:check && pnpm test — CI can't be relied on.
  • Manual smoke: build, pnpm pack, pnpm add -g the tarball, then substrate install-skill against a throwaway ~/.claude/skills and confirm substrate diagnose flips from drift → ok.

Rollout

  • Ships as a normal dev-board change (feature branch off dev → PR into dev), gated by the usual tests_green → two-reviewer reviews_approved → Diego's diego_approved.
  • Docs land in the same PR: RELEASING.md "After a release" gains the skill-refresh step; the "Publishing to npm" files note gains skills.
  • Release board update lands in the same PR: .substrate/boards/release.json Released-gate message becomes "reinstall the binary and refresh the skill". Because the board description already frames "skill refresh" as a Release-Engineer duty, this closes the gap between stated intent and the enforced gate.
  • First real exercise is the next release: after tagging and reinstalling the global binary, run substrate install-skill and confirm substrate diagnose reports the skill current. From then on, drift is a one-command fix and a diagnosable state instead of a silent, human-caught bug.
  • Backward-compatible: the command is additive; existing flows are untouched if it's never run. No migration.
