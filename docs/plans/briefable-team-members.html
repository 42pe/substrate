PLAN — Briefable team members

dev board · task 15d45ca7 (briefable-team-members) · Draft v1 — awaiting plan_approved · spec →

Approach

The mechanism is small and lands almost entirely as additive optional fields on paths that already exist. The v0.7.0 member layer did the structural work: a registry, a binding, a resolver, an advisory warning channel, and a UI card. This adds one nested object to two schemas and lets it flow.

Three properties of the existing code make this cheap, and one makes it a real change rather than a docs edit:

  • getBoardSubstrateHandler splices the whole Member object into the payload by reference (src/mcp/tools/read/get-board-substrate.ts:70-77), so the registry brief reaches MCP, HTTP and the UI the moment it survives parsing.
  • GET /api/boards/:id reuses the MCP handler verbatim (src/http/routes/api/index.ts:63-66) — zero HTTP work.
  • The warning channel (Substrate.warnings: string[], printed by substrate validate, counted by diagnose) already exists and already exits 0.
  • The blocker: every schema in src/substrate/schemas.ts is a plain z.object — zod’s default strip. A brief written into a member file today parses fine and is silently discarded. That is the one thing that must change in code before any content authoring has any effect, so it is Step 1.

Ordering principle: mechanism first, content second, and content is the bulk. Steps 1–4 are perhaps a third of the work; Step 5 (authoring 12 member records and one board binding, then de-duplicating concerns against guardrails) is the rest, exactly as the roadmap plan predicted.

Step-by-step work

Step 1 — Types + schemas (the field must survive parsing)

  • src/core/types.ts: add the Brief interface with the docblock from the spec (it carries the “no spawn mechanics” boundary — that comment is load-bearing and should not be trimmed). Add brief?: Brief to Member and to TeamBinding.
  • src/substrate/schemas.ts: add BriefSchema (plain z.object, all keys optional, strings .min(1), guardrails: z.array(z.string().min(1)).optional()). Add brief: BriefSchema.optional() to MemberSchema and TeamBindingSchema.
  • No change to Substrate, so this avoids the ~18-file synthetic-literal churn that the members work caused in 00504e5. Verify that claim by running the suite before touching anything else.

Test now, before going further: a member JSON carrying brief round-trips through MemberSchema with the field intact, and a TeamBindingSchema parse keeps a binding brief. Both fail on main; both pass after this step. That is the regression proof for AC2.

Step 2 — Read-surface pass-through

  • src/mcp/tools/read/get-board-substrate.ts: add brief?: Brief to both arms of the ResolvedTeamMember union (the unresolved: true arm included — a board-local brief survives a dangling member ref, per AC5). In the map at line 70, spread the binding’s brief: ...(binding.brief ? { brief: binding.brief } : {}) — conditional so an absent brief adds no key, matching the codebase’s policies_fired idiom.
  • Deliberately no merging. The handler does not concatenate strings, union arrays, or key-wise override. Two objects out; the consumer composes.
  • ui/src/lib/api.ts: mirror the union change (lines ~101-110). This is a hand-maintained duplicate of the server type — it will not error if forgotten, so it is on the checklist rather than left to the compiler.
  • Update the get_board_substrate tool description’s team[] sentence (currently at get-board-substrate.ts:103) to name both briefs, state the composition rule, and repeat that the brief is descriptive — confers no permission, launches nothing. Keep it to one added sentence: this string is in every orienting agent’s context.

Step 3 — The brevity lint

  • src/substrate/validator.ts: a pure checkBriefBrevity(label: string, brief: Brief | undefined, warn), called from checkRegistryIntegrity (label Member '<id>') and from checkTeamIntegrity (label Board '<board>' team member '<id>').
  • Constants in one exported block: BRIEF_MANDATE_MAX = 280, BRIEF_DELIVERABLE_MAX = 280, BRIEF_GUARDRAIL_MAX = 200, BRIEF_GUARDRAILS_MAX = 5. Named so retuning is one diff.
  • Message strings follow the existing validator format exactly (see the four current strings at validator.ts:73,103,110,117) and end with the word Advisory.
  • Because it runs inside validateSubstrate, it reaches all three existing sinks for free: Substrate.warnings (load → validate/diagnose), and teamCtx.warn on the update_board write path (log-only). No new plumbing.
  • Nothing about it can fail a load or refuse a write; assert that explicitly in a test, not just by inspection.
This step is the only part of the plan the roadmap did not ask for. It is isolated to one function and one call site pair so it can be dropped whole if Diego says no (spec Q1).

Step 4 — UI: render the brief in the Team card

  • ui/src/routes/BoardDetail.tsx, TeamCard (lines ~162-221). After the existing full_description / Traits: / Concerns: lines, add, all conditional:
    • Mandate: — the imperative sentence, in normal text.
    • Deliverable: — same treatment.
    • Guardrails: — a small list rather than a comma join; these are read one at a time, unlike traits.
  • Board-local brief renders under a small on this board label so a reader can tell the two apart without opening the JSON. This is the human half of “side by side, never merged”.
  • Keep it inside the existing collapsed <details> disclosure — no new card, no layout change.
  • The unresolved arm keeps rendering id + unresolved badge, now plus a board-local brief when the binding carries one.

Risks & mitigations

Risk Mitigation
The kill signal fires: briefs read as generic, so orchestrators keep hand-writing them. The plan says this would mean the missing piece was task context, not member definition. Step 5 is written as prose by a human/agent pass, not templated. The acceptance bar is “would you paste this?” — if a mandate restates the member’s name, it has failed. Watch for it in dogfood over the 4 weeks the plan names.
Drift back into a second CLAUDE.md. Briefs grow every time someone has a thought. The brevity lint (Step 3), plus the composition rule keeping board-specific text out of the shared record.
Silent strip. Someone authors a brief against a binary that predates Step 1 and sees nothing happen — no error, no warning. Nothing to do in code (strip is zod’s default and matching it keeps the schemas uniform), but the regression test in Step 1 and a CHANGELOG line make the version boundary explicit.
The UI duplicate falls out of sync — ui/src/lib/api.ts re-declares ResolvedTeamMember and will not fail to compile if forgotten. Explicit checklist item in Step 2; the BoardDetail test renders a brief, so a missed mirror shows up as a type error there.
Guardrails read as enforcement. The word invites “Substrate stops me doing this”, which is false. Say it in three places: the Brief docblock, the tool description, AUTHORING.md. The whole member layer is already documented as descriptive; this keeps that line intact.
Hand-edit vs. in-flight write on release.json. Board version is an OCC key, and a hand edit that does not bump it lets a concurrent update_board CAS pass against a stale-but-equal number. Step 5c bumps it. Make the edit when no agent is mid-write on that board.
Template multiplier overclaimed while ba3b8c01 is open. Spec says so explicitly; do not write the claim into README until add can carry members.

Test strategy

Every existing member/team test file is the template; extend rather than invent. Local gate only — CI is billing-blocked.

  • src/substrate/member-schema.test.ts — a member with a full brief parses and retains it; a member with a partial brief (mandate only) parses; a binding with a brief parses; brief: { mandate: '' } rejects; guardrails: 'nope' rejects; a member with no brief still parses (backward compat).
  • src/substrate/validator.test.ts — one warning per over-long mandate / deliverable / guardrail entry / oversized guardrails list, on both the registry and the binding, with the label naming the board for the latter; a within-limits brief is inert; validateSubstrate never throws; checkTeamIntegrity never throws.
  • src/substrate/loader.test.ts — a member file with a malformed brief is warned and skipped while its neighbours still load (inherits the existing warn-and-skip assertions).
  • src/mcp/tools/read/get-board-substrate.test.ts — registry brief appears inside member; binding brief appears as a sibling and is not merged into member; the shared-member case (two boards, same member) returns an identical member object and different sibling briefs — the AC4 test, modelled on the existing groups version; a binding brief on an unresolved member is returned alongside unresolved: true.
  • src/cli/commands/validate.test.ts — a substrate with an over-long brief prints the warning and exits 0. (There is no member-specific case in this file today; this adds the first.)
  • tests/integration/board-team-migration.test.ts — extend the live-.substrate/ assertions: all 8 members carry a mandate, a deliverable and ≥1 guardrail; reviewers.full_description contains no board-specific clause; the release binding for reviewers carries a brief and the dev one does not; s.warnings is still [].
  • tests/integration/example-substrate.test.ts + src/cli/templates/index.test.ts — the parse-equal drift check already covers the two mirrors; add that all 4 bundled members carry a brief and that loadTemplateMembers still throws on a malformed one (the strict-defaults gate).
  • src/http/routes/api/api.test.ts — GET /api/boards/:id surfaces both briefs (proves the free pass-through did not regress).
  • ui/src/routes/BoardDetail.test.tsx — a member with a brief renders mandate, deliverable and each guardrail; a board-local brief renders under its own label; a member with no brief renders exactly as today; the Team (0) / No team declared. and unresolved cases are unchanged.
  • Manual, once: substrate serve and read the dev and release Team cards — the real check is whether the release Reviewers entry now tells a reader something the dev one doesn’t.

Local gate before tests_green: pnpm build, tsc --noEmit at the root and in ui/ (the root build skips test files), pnpm lint, pnpm format:check, pnpm test, plus substrate validate against the live .substrate/.

Rollout

  1. Branch off dev. One PR into dev; never main.
  2. Commits in step order — feat(members): brief on the member record and the board binding, then a separate chore(members): author briefs for the live team so the mechanism diff stays reviewable apart from the prose diff.
  3. Two independent reviewers, distinct lenses. Suggested split: (a) schema/back-compat — does a pre-brief project still load byte-identically, is the lint truly non-blocking; (b) content/product — do the twelve briefs pass the “would you paste this?” bar, and is the concerns/guardrails line actually held.
  4. Zero migration. No DB change, no schema version bump, no data backfill. Older projects load unchanged; older binaries reading a newer member file strip the brief silently (forward-compatible by accident, and harmless — the layer is advisory).
  5. Dogfood window: the roadmap plan asks for 4 weeks. The observable is whether coordinator prompts start quoting the board instead of composing a brief. Record it in the dogfood journal; if they don’t, the plan’s kill signal has fired and the answer was task context, not member definition.
