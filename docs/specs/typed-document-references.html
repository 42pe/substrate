Problem

Substrate models the shape of work and knows nothing about the artifacts the work consumed or produced. Every document a task depends on is buried in prose or hand-jammed into a bespoke field invented board by board. We are doing this in three places, incompatibly:

  • The dev board invented spec_doc: one markdown field holding two links glued together — [Spec](docs/specs/x.html) · [Plan](docs/plans/x.html).
  • The shipped web-delivery template — the thing a new user is handed — independently invented three fields for the same job: spec_doc, plan_doc, audit_doc, all type: 'string' (src/cli/templates/web-delivery.board.ts:38-46).
  • The release board’s docs-verification gate enumerates every document the release touched by reconstructing it from git log, every time.

Three boards, three vocabularies, zero shared meaning — and, decisively, nothing checkable. There is no “the spec” to resolve, only a string that happens to contain brackets. A dangling link is indistinguishable from a live one until a human clicks it.

Goals

  • The references are true. Resolution checking is the core; everything else is a consequence of it.
  • Roles, not a bag of strings. A reference carries a role (spec, plan, reference, design as the starting vocabulary), and a board declares which roles it expects. Per the plan: if roles get cut, cut the feature.
  • Repo-relative, enforced at the point of writing. Absolute paths and paths escaping the repo are refused with a message that says why.
  • Per-task visibility for agent and human, with dead references marked dead.
  • A minimal per-board listing, filterable by stage and role.
  • One vocabulary replaces three. Migrate dev off spec_doc; retire the template’s three fields.
  • Remove the .substrate/attachments/ scaffolding and correct the PRD.
  • Advisory, always. A dangling reference is surfaced, never fatal — matching the member registry’s posture exactly.

Non-goals

Carried literally from the approved plan.

  • Untyped attachments. A list of paths with no role is spec_doc with extra ceremony.
  • URLs, PR links, issue links, Figma links — any non-path reference. They cannot be resolution-checked, which is the one thing this feature is for. The dev board already has a pr field and that is the right shape. This is the scope creep that would sink the feature, and it is out.
  • Storing, copying, uploading, serving, previewing, rendering or diffing document contents. References only. No size limits, no binary handling, no attachment routes.
  • Attachments on comments. Tasks only.
  • Automatic discovery, inference or backfill of which documents belong to a task. Declared, or absent.
  • An artifact-centric index (one document listed once with all its referrers).
  • Ordering, captions, descriptions or any per-reference presentation metadata.
  • A UI for adding or editing references. The inspector displays; it does not author.
  • A gate that requires references to resolve. The right eventual answer, parked deliberately — it changes how gates are evaluated. (It is also already on the roadmap as “gates backed by verifiable evidence — command exit codes / CI status / file existence”, decisions.md:145.)
  • Anything named “attachments.” The word carries the copied-file model this plan exists to end.

Design — a new field_schema type, not a new entity

The plan leaves the mechanism to this spec. The answer that costs least and fits the product best is a new field type in the board’s own field_schema: 

// .substrate/boards/dev.json
"field_schema": {
  "task": {
    "documents": {
      "type": "document_refs",
      "roles": ["spec", "plan"]          // THE BOARD DECLARES ITS VOCABULARY
    },
    ...
  }
}

// a task's custom_data
"documents": [
  { "role": "spec", "path": "docs/specs/typed-document-references.html" },
  { "role": "plan", "path": "docs/plans/typed-document-references.html" }
]
// src/core/types.ts
export interface FieldSchemaEntry {
  type: 'string' | 'number' | 'boolean' | 'enum' | 'markdown' | 'string_list' | 'document_refs';
  required?: boolean;
  format?: string;
  values?: string[];   // required when type = 'enum'
  roles?: string[];    // REQUIRED when type = 'document_refs' — the board's role vocabulary
  human_only?: boolean;
}

/** One typed reference to a document that lives in the repo. */
export interface DocumentRef {
  role: string;   // must be one of the declaring field's `roles`
  path: string;   // repo-relative, forward slashes, no `..`, no leading `/`
}
Why a field type and not a new first-class entity. Five things fall out for free, and each would otherwise be new code:
  • Per-board role vocabulary is exactly what field_schema is for — it is the mechanism enum/values already uses.
  • Write-time enforcement lands in src/substrate/field-validator.ts, which every write already calls with touched_keys. Refusing an absolute path is one more checkType arm.
  • Storage is custom_data — no table, no migration, no BINARY_SCHEMA_VERSION bump.
  • The split the plan asks for happens by construction: “a board’s role vocabulary travels with a template, while the paths stay behind with the tasks.” Field schema is board config (travels in a template); custom_data is task state (stays in the gitignored DB). That is the correct split, and it is free.
  • A second board wanting documents declares the field — it does not invent a fourth string field. That is the whole “one vocabulary instead of three” goal.

roles is required when type is document_refs, mirroring values for enum. A board that cannot say what its roles mean has the feature the plan told us to cut.

Write-time enforcement — string validation only, no filesystem

A document_refs value is rejected with schema_violation when:

Rejected Why
Not an array of { role, path } objects Shape
role not in the field’s declared roles Roles are the feature
Absolute path (/Users/…, C:\…, ~/…) The go-live exposure scrub exists to strip /Users/diegoferreyra/… out of tracked files; a first-class agent-written path field would manufacture that at scale
Escapes the repo (any .. segment surviving normalisation) Portability + exposure
Contains a URL scheme (https://, file://) Unverifiable — the hard non-goal
Backslash separators, empty path, empty role One canonical form
Duplicate (role, path) pair Nothing means anything different the second time
The write path never touches the filesystem. It validates the string and stops. Two reasons, both load-bearing: writes stay pure and fast (the validator is called on every create_task/update_task), and referencing a document you are about to write must be legal — the Planner links the spec, then authors it. Resolution is a separate, advisory, read-time concern. That separation is what lets the check be strict about form and gentle about existence.

Resolution checking — the core

A pure function resolveDocumentRefs(repoRoot, refs) → { role, path, exists }[]. The repo root is the parent of the .substrate/ directory — the same convention substrateRootFromCwd(cwd) = join(cwd, '.substrate') already establishes. Each path is joined, canonicalised, asserted to sit under the repo root (reusing assertPathUnder, which is written and tested), then existence-checked.

Surfaced in the plan’s stated priority order:

  1. substrate validate — the CI-friendly lint and the natural home for “your substrate says things that aren’t true”. One advisory warning per dangling reference, on the existing substrate.warnings channel. Exit code stays 0.
  2. The inspector’s task detail — a Documents section, dead entries marked dead, via GET /api/tasks/:id/documents.
  3. The board listing — GET /api/boards/:id/documents, rendered on the board detail page, filterable by group and role, marking dead entries rather than omitting them. An index that hides its own rot is the failure the raw idea correctly feared.
A decision the plan did not cover: substrate validate is DB-free today. It calls loadSubstrate(root) and nothing else — it never opens data.sqlite. Document references live in task custom_data, which is in the DB, and the DB is gitignored — in CI there is no database at all.

Resolution: validate opens the database if the file is present, using openClient (which does not migrate — a lint must never migrate a user’s data). If the file is absent, or its schema version is ahead of the binary, it prints one line — Document references not checked (no database at <path>). — and still exits 0. So CI keeps validating boards and policies exactly as today, and a developer with a local DB gets the document check. This is the honest shape; the alternative (making validate require a DB) would break the CI use case the command exists for.

Where the listing lives — a decision the plan left open

The plan asks for “one minimal listing … chosen for where it is actually consumed”, and says plainly that this is its weakest part. Choice: the inspector, not a CLI command and not an MCP tool.

  • Not MCP — no agent has this question. An agent picking up a task asks about its task, which get_task already answers. Adding a tool would pay the documented context tax for no asker.
  • Not a new CLI command — the human asker (the release docs auditor) is served by substrate validate’s dangling warnings for the part that matters, and a whole command for the weakest item in the plan is not proportionate.
  • The inspector — it is where a human already browses a board, it costs one read route and one panel, and the plan already ranks it second in the warning priority order.

Acceptance criteria

  • AC1. FieldSchemaEntry.type accepts 'document_refs', with roles: string[]. A document_refs declaration with no roles, or an empty roles, is rejected at board load with an actionable error — the same tier as an enum with no values.
  • AC2. A write of a well-formed array of { role, path } whose roles are all declared succeeds.
  • AC3. Each rejection case in the enforcement table returns schema_violation naming the field and saying why: an absolute path, a .. escape, a URL, a backslash, an undeclared role, a non-array, a malformed element, a duplicate pair.
  • AC4. The write path performs no filesystem access — proven by a test that writes a reference to a path that does not exist and asserts the write succeeds.
  • AC5. resolveDocumentRefs reports exists correctly for a present file, an absent file, and a path that resolves outside the repo root (which is reported as unresolved rather than read).
  • AC6. substrate validate emits one advisory warning per dangling reference, naming board, task id, role and path — and exits 0.
  • AC7. With data.sqlite absent, substrate validate prints the “not checked” line, still lints boards and policies, and exits 0. It never runs a migration.
  • AC8. A board load never fails because of a document reference, dangling or malformed-on-disk. Advisory, always — matching the member registry.
  • AC9. GET /api/tasks/:id/documents returns each reference with its exists flag; the inspector’s task detail renders them with dead entries visibly marked.
  • AC10. GET /api/boards/:id/documents lists every active task’s references for that board, filterable by group and role, including dead ones, marked.
  • AC11. get_task returns the references (they are custom_data, so this is inherited). Known consequence: because the value is an array, list_tasks’ summary view drops it into custom_data_omitted (src/core/task-summary.ts keeps only small scalars). That is correct behaviour and is documented, not worked around — the per-task read and the listing endpoint are the intended surfaces.
  • AC12. All 7 dev tasks carry typed spec + plan references; every one resolves; no task retains a spec_doc key; dev.json no longer declares spec_doc and is at version 11; the two policy messages name documents.
  • AC13. The web-delivery template declares documents with three roles and no *_doc string fields, in both mirrors, with the parse-equal drift test passing.
  • AC14. attachmentsDir and attachmentTaskDir no longer exist; substrate init creates no attachments/ directory and writes no gitignore line for it; path-canonical.ts is still present, still tested, with a corrected comment; prd.md describes references rather than copies; the word “attachments” survives nowhere as a Substrate feature.
  • AC15. No database migration. BINARY_SCHEMA_VERSION unchanged at 2.
  • AC16. No gate anywhere requires a reference to resolve; no write is refused because a file is missing.

Open questions (for Diego)

Q1 — A field type rather than a first-class entity. Recommended above. The trade-off: references ride in custom_data, so they inherit its behaviours — including being omitted from list_tasks summaries (AC11). Worth confirming, because it is the one visible cost.
Q2 — validate opens the DB when present. The plan calls validate the natural home but the command is DB-free today and the DB is gitignored. The proposal keeps CI working and checks locally. Alternative, if you would rather validate stay strictly substrate-as-code: put the dangling check only in the inspector and drop AC6/AC7. That costs the CI-shaped surface the plan wanted most.
Q3 — Field name documents, role names spec/plan/reference/design. The dev board only declares spec and plan; the wider vocabulary is documentation for other boards. The template adds audit. Push back on any of these names now — they are the part that is hard to change later.
Q4 — Listing in the inspector only. Reasoned above. If the release docs auditor wants it at a terminal, the cheapest follow-on is --json on a future validate, not a new command.
