SPEC — substrate activity

dev board · task 847358dc (substrate-activity) · Draft v1 — awaiting plan_approved · plan →

Roadmap authority: 34e8defa “the reality counterpart to explain” (roadmap_approved 2026-09-06). The name is settled there: activity, not tail, not supervise, not observe.

Problem

substrate explain renders the process you designed — per board, an inline-SVG flow diagram plus field and policy tables, read from substrate-as-code and never opening the database. There is no counterpart for the process that ran. The board author’s central question — did the workflow I wrote get used the way I meant it to? — has no answer in the product.

Two of its sub-questions depend on data that exists nowhere but the event log:

  • move_blocked — a transition_guard rejected a move. The write rolled back, so the task carries no trace it was attempted (src/mcp/tools/write/update-task.ts:219-247 writes the event out-of-band, precisely because the transaction is gone). A board where an agent bounced off the same gate for two days looks identical to one where nothing happened.
  • policies_fired — which policies engaged on a successful write. It is the only record of whether the agent_responsibility class does anything at all, and the PRD’s single load-bearing metric is “% of writes engaging ≥1 agent_responsibility policy”. Today that number is readable only by starting substrate serve and eyeballing a paginated HTML page. The product cannot count the thing it says it is judged on.

And the reach problem, which the code states in its own header:

// src/http/routes/api/activity.ts:7
Project-wide activity feed (Theme 4a) — HTTP-only, NOT an MCP tool.
...
Agents don't need this (they read per-task history via get_task_history), so it stays
off the MCP surface — same precedent as /api/health and /api/boards/:id/columns.

get_task_history requires knowing which task to ask about — exactly what you do not know when the question is about the shape of the flow. An agent’s only route to a cross-board view today is to have a human start serve and speak HTTP to a local port, outside its own tool surface.

Finally, the feed itself is thinner than the questions require:

  • listProjectEvents (src/storage/repositories/events.ts:99-145) takes no filters at all — only pagination. No board, no event type, no actor, no window.
  • It is newest-first only. That answers “the last N”; it cannot answer “everything after point X”, which is what a repeated review needs.
  • There is no aggregate shape. A design question (“which gate blocked most this month”) is answerable only by paging thousands of raw rows into a context window — i.e. not answerable.

Goals

  • A cross-board activity read on the agent surface. One call, no task id known in advance, bounded. This is the feature; the terminal command is the small half.
  • Counts over a window — transitions per stage pair, blocks per gate, engagements per policy, activity per board and per actor. A fixed, bounded payload by construction, so a design question costs one call and a predictable number of tokens.
  • The PRD metric becomes a field. responsibility_engagement_rate — writes engaging ≥1 agent_responsibility policy, over writes — read directly instead of transcribed from a web page.
  • Filters that surface the signal: board, event type (with blocked transitions first-class), actor, time window, and a policy selector that catches policy engagement, which is not an event type.
  • Resumability — “what has happened since I last looked”, exactly, with no re-reading and no de-duplication.
  • The same read from a terminal, bounded and filtered, for when serve is not running.
  • Honest framing throughout. Actor names are self-attested; this is not an audit trail, not oversight, not accountability.

Non-goals

Carried literally from the approved plan.

  • No --follow, live tail, or any long-running watch command. Cut deliberately: a design question is asked of a window of history, never of the last four seconds, and a live tail costs the primary persona their one terminal for something with no action attached. The browser Activity page is the ambient surface.
  • No SSE, websockets, or any streaming/push transport.
  • No board-health analysis engine. No conformance scores, no “this gate is mis-authored”, no recommendations, no findings, no thresholds, no verdicts. Substrate supplies data; the agent reasons.
  • No change to substrate explain, and in particular nothing that makes it require the database. Pair, don’t merge.
  • No notifications of any kind. Pull-only.
  • Nothing that acts on what it sees — no auto-nudging, no auto-commenting, no rules engine over events. That is the deferred automation policy class, and it is also why the command is not called supervise.
  • No scheduling or cron.
  • No reinventing state queries. Stale / stuck / unfilled is list_tasks (updated_before, group_id, missing_required_fields). No second, event-shaped way to ask a state question.
  • No merging with substrate logs, and no piping application errors into activity.
  • No new event types, no richer per-field diffs, no change to what gets recorded. Reach-and-filter over events already written.
  • No per-agent performance measurement or ranking. The data is self-attested; the subject is the board, not the workers.
  • No retention, pruning, or archiving of event history.
  • No cross-project or multi-machine activity, and no new network exposure.
  • Never framed as an audit trail, oversight, or accountability mechanism.

Scope

  • 1. A shared aggregate at src/operations/activity.ts, following the list-pending-approvals.ts precedent — one definition of “activity”, three surfaces.
  • 2. Repository surface: filters + an ascending, resumable read + the count queries, in src/storage/repositories/events.ts.
  • 3. One MCP read tool, activity — the feature.
  • 4. substrate activity — the same read, printed, with --json at parity.
  • 5. GET /api/activity gains the same filters, moving onto the shared aggregate so the three surfaces cannot disagree.
  • 6. Cross-references between activity, logs and explain so the three are not confusable.

Reversing a recorded decision — stated head-on

The “HTTP-only, NOT an MCP tool” call is written down twice (src/http/routes/api/activity.ts:7, src/http/routes/api/index.ts:159-160) with a stated rationale: “Agents don’t need this (they read per-task history via get_task_history).” This spec reverses it, and the reversal is the feature.

The original rationale assumed the agent’s question is always about a known task. get_task_history serves that. It cannot serve the question this feature exists for — which task, which gate, which stage — because you must already know the answer to ask it. The precedent cited (/api/health, /api/boards/:id/columns) holds for those two: health is a process-liveness probe an agent has no use for, and the kanban aggregate is a rendering shape for a UI. Neither is a question an agent cannot otherwise answer. Cross-board history is.

The cost is real and acknowledged: decisions.md flags the MCP surface as carrying a context tax and names a slimmer default toolset as a future direction. This adds exactly one tool — 32 → 33 — and deliberately does not add a family (no activity_counts, no list_transitions). The two shapes ride one tool on a view parameter, which is the precedent list_tasks already sets. The code comments that record the old decision get corrected in the same change, not left to contradict the shipped tool.

The read — one tool, two shapes

Input

activity({
  view?: 'events' | 'counts',     // default 'events'
  filters?: {
    board_id?: string,            // single board; omit = every board
    event_types?: TaskEventType[],// 'move_blocked' is a first-class selection
    actor?: string,               // exact match on actor_agent_name
    policy_id?: string,           // policy ENGAGEMENT — see below
    since?: string,               // ISO 8601, inclusive
    until?: string,               // ISO 8601, inclusive
    since_event_id?: number       // resumability watermark — see below
  },
  pagination?: { cursor?: string, page_size?: number },  // events view only
  counts_limit?: number           // counts view only; per-breakdown cap, default 20, max 100
})
policy_id is the filter that makes policy engagement first-class. Policy engagement is not an event type: policies_fired rides inside the changes JSON of created/updated events, and a guard rejection is a separate move_blocked event whose changes.policy_id names the guard. One filter covers both: policy_id matches a move_blocked whose changes.policy_id equals it, or a write event whose changes.policies_fired[] contains it. Without this, “which gate blocked most” and “is this policy engaging at all” are both unaskable.

Resumability — since_event_id

The plan flags this as a real gap: today’s feed is a newest-first pager, which answers “the last N” but not “everything after point X”. The fix uses a key that already exists — task_events.id is an INTEGER PRIMARY KEY AUTOINCREMENT, chosen in migration 002 specifically so ordering is free when occurred_at ties at millisecond resolution.

Default (no since_event_id) With since_event_id
Order Newest first (occurred_at DESC, id DESC) — today’s behaviour, unchanged Oldest first (occurred_at ASC, id ASC)
Question answered “What are the last N things?” “Everything after this point, in order.”
Predicate cursor tuple, as today e.id > ?

Every response — both views — carries a watermark: the highest task_events.id the query observed within the filter window, or null when nothing matched. Store it; pass it back as since_event_id; get exactly the new events, once. No overlap, no de-duplication, no timestamp arithmetic.

Why the rowid and not occurred_at: two events can share a millisecond, and the whole reason the id is an integer rowid rather than a uuid is to break that tie. A timestamp watermark would either drop an event or repeat one on every tie.

Output — view: 'events'

Identical in shape to today’s /api/activity rows, plus the watermark, so the UI and the tool render the same thing: 

{
  results: [{
    id, task_id, event_type, changes, actor_agent_name, occurred_at,
    task_title,   // LEFT JOIN tasks — null if the task row is gone
    board_id,     // LEFT JOIN tasks — null if the task row is gone
    board_name    // resolved from substrate-as-code in TS — null if the board was removed
  }],
  pagination: { next_cursor, has_more, page_size },
  watermark: 4821 | null
}

Output — view: 'counts'

The decisive design question, per the plan: the counts shape is what makes the feature usable at all. Bounded by construction — a fixed set of breakdowns, each capped at counts_limit entries with an explicit truncated flag. No matter how many events the window spans, the payload size is a function of counts_limit alone. 

{
  window: {
    since: '2026-08-06T00:00:00.000Z' | null,
    until: null,
    since_event_id: null,
    events_matched: 812,
    watermark: 4821
  },
  writes: {
    total: 640,                              // created + updated events in-window
    engaging_responsibility: 191,            // ≥1 agent_responsibility entry in policies_fired
    responsibility_engagement_rate: 0.298    // the PRD metric, as a ratio. NOT a verdict.
  },
  by_board:      [{ board_id, board_name, count }],       // capped, desc
  by_event_type: [{ event_type, count }],                 // all 8, no cap needed
  by_actor:      [{ actor, count }],                      // capped, desc
  transitions:   [{ board_id, from_group, to_group, count }],  // capped, desc
  blocks:        [{ board_id, policy_id, policy_name, from_group, to_group, count }],
  policies:      [{ policy_id, policy_name, policy_type, count }],
  truncated: { by_board: false, by_actor: false, transitions: false, blocks: false, policies: false }
}
Breakdown Derived from Answers
transitions updated events where changes.before.group_id differs from changes.after.group_id Are tasks flowing in the intended order? Are there dead stages?
blocks move_blocked events, grouped on changes.policy_id Which gates block most — healthy friction, or a mis-authored guard?
policies changes.policies_fired[] on write events Is a policy engaging at all?
writes.* The same array, counted per-write rather than per-entry The PRD’s load-bearing metric.

policy_name and the group ids are joined from substrate-as-code in TypeScript — the same split board-columns.ts already uses, since policies live in board JSON and events live in SQLite. A policy id no longer present in any board is returned with policy_name: null, not dropped.

A ratio is not a verdict. responsibility_engagement_rate is a count divided by a count, and the roadmap plan names that exact percentage as the metric to make countable. There is no threshold, no target, no colour, no “healthy/unhealthy”, in any surface. The 20%/35% figures live in the PRD and stay there.

Two honesty constraints the data itself imposes

1. policies_fired in practice contains only agent_responsibility entries. runTransitionGuards always returns [] (src/policy/engine.ts:78) — per B6, a guard that engages and passes contributes nothing. So a “policies engaged” count is a responsibility- engagement count, and a passing guard is invisible everywhere. The policies breakdown keeps policy_type so this is visible in the data rather than assumed, and the tool description says it outright. Changing what gets recorded is an explicit non-goal, so this is documented, not fixed.
2. move_blocked counts are a lower bound. The event is written out-of-band on deps.client after the guarded transaction rolled back, and a failure to write it is logged and swallowed (update-task.ts:239-246). Deliberately — recording the block must never mask the original error. The consequence is that blocks counts what was successfully recorded, which is a floor. Say so in the tool description and in --help.

And the constraint the plan names: actor_agent_name is a free-form, self-attested string, and it mixes kinds — MCP writes stamp the caller’s agent_name, while substrate approve/unapprove stamp human:<os-user>. by_actor is a supporting filter, never a headline, and is never framed as attribution or performance.

The terminal half

substrate activity [--board <id>] [--type <t>[,<t>...]] [--actor <name>]
                   [--policy <id>] [--since <iso>] [--until <iso>]
                   [--since-event <id>] [--counts] [-n <N>] [--json]
  • Default: the 20 most recent events across every board, as an aligned table.
  • --counts prints the counts view instead.
  • --json emits the structured result at parity with the MCP tool — never colourised, honoured on a TTY, valid for the empty case. Same contract as pending-approval --json.
  • Two distinct empty states, following substrate logs’ precedent: no events at all (nothing has happened) vs. no events matching this filter.
  • The printed footer names the watermark — Resume with: --since-event 4821 — so the terminal user gets resumability too.

Cross-references — three commands, three stores

Reads Answers
substrate explain boards/*.json — never the DB What did I design?
substrate activity task_events in SQLite What actually happened?
substrate logs .substrate/logs/substrate.log What broke?

The seam is sharper than it looks: logHandledError deliberately skips transition_blocked from the error log (src/mcp/wrapper.ts:114) because it is already recorded as a move_blocked event. So a blocked gate is absent from logs exactly to the extent it is present in activity. That pairing is currently undocumented and is the single most useful cross-reference to add.

substrate validate is the static sibling worth naming too: it warns that a guard can never fire, from the config alone; activity shows that a guard never did. Same instinct, different evidence — a one-line pointer in each, no shared vocabulary, no merge.

Acceptance criteria

  • AC1. An MCP tool named activity is registered (tool count 32 → 33) and returns cross-board events in one call, without a task id. No other new tool ships.
  • AC2. Each filter works alone and in combination: board_id, event_types, actor, since, until. Combining them is AND.
  • AC3. policy_id returns both the move_blocked events that guard rejected and the write events whose policies_fired contains it — proven by a test that seeds one of each and asserts both come back.
  • AC4. since_event_id returns strictly newer events in ascending order. A resume loop over a seeded stream yields every event exactly once, with no gap and no repeat, including when two events share an occurred_at.
  • AC5. Every response carries a watermark: the highest event id observed within the filter window, or null when nothing matched.
  • AC6. view: 'counts' returns the fixed breakdown set. Payload size is a function of counts_limit only: a test seeding an order of magnitude more events leaves the serialized size within a small constant factor.
  • AC7. A breakdown with more distinct keys than counts_limit returns the top N by count and sets its truncated flag.
  • AC8. transitions counts only real group changes — an updated event that touched no group_id, and one where before and after are equal, both contribute nothing.
  • AC9. writes.responsibility_engagement_rate equals engaging_responsibility / total, counts a write engaging two responsibility policies once, and is 0 (not NaN, not null) when total is 0.
  • AC10. blocks and policies carry policy_name joined from substrate-as-code, and a policy id absent from every board is returned with policy_name: null rather than dropped.
  • AC11. A board_id filter drops events whose task row is gone (board_id: null from the LEFT JOIN) — documented, tested, and stated in the tool description.
  • AC12. substrate activity prints a table; --counts prints the aggregate; --json is byte-equal to the MCP tool’s payload for the same filters; the two empty states are distinguishable; an unknown flag is rejected (ALLOWED_FLAGS_BY_COMMAND).
  • AC13. GET /api/activity accepts the same filters and keeps its existing default behaviour byte-identical when called with no filters — the UI Activity page must not change.
  • AC14. The MCP tool, the CLI and the HTTP route all go through src/operations/activity.ts. No second definition of a filter or a count anywhere.
  • AC15. No schema migration. BINARY_SCHEMA_VERSION is unchanged, no new table, no new column, no new event type, and no change to what any write records.
  • AC16. substrate explain still runs with the database absent — an explicit regression test, because the non-goal is explicit.
  • AC17. The tool description and --help state: the move_blocked floor, that policies_fired carries only agent_responsibility entries, that actors are self-attested, and that this is not an audit trail. The stale “HTTP-only, NOT an MCP tool” comments are corrected.
  • AC18. substrate --help distinguishes activity / logs / explain in one line each, and logs’ own text points at activity for blocked transitions.

Open questions (for Diego)

Q1 — No migration, no composite index. There is no (event_type, occurred_at) index, so a windowed count-by-type scans idx_task_events_occurred_at and groups in memory. Adding one means migration 003 and a BINARY_SCHEMA_VERSION bump — which makes every older binary refuse to open the file. Recommendation: ship with no migration; the dogfood DB is ~200KB and the plan sizes this as “cheap, the events are already recorded”. Revisit only if a real window is measurably slow.
Q2 — One tool with view, not two tools. Keeps the context tax at +1 and follows list_tasks’ existing view precedent. The cost is a response shape that varies by parameter. Confirming because the alternative (a separate activity_counts) is the more conventional API choice.
Q3 — counts_limit default 20. Enough for every breakdown on our three boards to be complete (8 event types, 3 boards, ~7 policies each). Set so truncated is normally false and the flag means something when it is not.
Q4 — Should GET /api/activity gain the filters now? Recommendation: yes, because it falls out of moving it onto the shared aggregate and the alternative is two filter implementations. The UI is not changed to use them in this task — that would be new UI scope.
