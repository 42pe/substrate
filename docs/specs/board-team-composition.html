SPEC — Data structures for per-board team composition

dev board · task 9a5af742 (board-team-composition) · Draft v4 — awaiting plan_approved · plan →

Problem

A board's team — the members that work it, each with traits and "Concerns" — lives today as free markdown prose inside the board's description field, under a ## Team heading. See it live in .substrate/boards/dev.json (Planner / Builder / Reviewers ×2 / Integrator) and .substrate/boards/release.json (Doc Auditor / Release Engineer / Validator / Reviewers ×2). Because it is prose baked into one big markdown blob, the team is:

  • Not queryable. Nothing can answer "which members work the Review group?" or "list the Planner's concerns" without a human re-reading the paragraph. The get_board_substrate payload returns groups, field_schema, and policies as structured data, but the team hides inside a description string.
  • Not renderable as data. The UI (ui/src/routes/BoardDetail.tsx) renders the description as one markdown block; it cannot show which members are associated with which groups, cross-link a member to a group, or present the roster as a first-class card the way it already does for field schema and policies.
  • Not a persistent identity. This is the decisive gap. A prose line under a board's description is local to that board. But a member can deliberately span multiple boards and multiple stages under one shared identity and one shared memory. A per-board roster line simply cannot express that.
  • Prone to drift. The prose roster and the board's agent_responsibility policies (src/policy/agent-responsibility.ts) both describe "who works in which group", in two places, with nothing keeping them consistent.

The motivating case: a persistent, cross-stage member

Consider an Oversight member that authors the spec at the start of a change (targeting the spec group) and then returns at the end to review the implementation (targeting the review group) — the same identity, drawing on the same memory pool, specifically so it can catch drift between the built thing and the goal it originally wrote down. That member may also sit on other boards. A team line nested in one board's JSON cannot model a cross-board, cross-stage identity with continuity; that demands a first-class member entity that exists once, at the project level, and is referenced by boards. That is the core of this proposal.

Goals

  • A first-class member entity, project-level. A member (id, name, description, traits, concerns, a memory pointer) is defined once in a project-level registry and can be referenced by any number of boards — one shared identity across boards and stages.
  • A thin board-level binding. Each board declares its team as references to members plus the part that is genuinely board-specific: which group(s) the member is associated with on that board.
  • Structured & queryable + renderable. Both layers are machine-readable and joined on read so the UI/agents see resolved members (name, description, group-assignment badges), not bare ids.
  • Shared memory falls out for free. Because a member is one entity with one memory pointer, two boards that bind the same member share that member's memory by construction.
  • Fully optional & additive. The whole member layer is opt-in: a project may keep its roster in the board description prose and never adopt the registry. Integrity mismatches are non-blocking warnings, never failures (see below).
  • Descriptive, not enforced. The registry and bindings describe intent for humans, UI, and orchestrators; Substrate gates nothing on them.
  • Single source of truth (when adopted). After migration the roster lives only in the registry + bindings; the prose ## Team section is removed from the description.
  • New projects get a real team out of the box. substrate init and the bundled template ship a coherent members registry + bindings, not an empty team.
  • Backward compatible. The registry and a board's team are both optional: boards with no team, projects with no registry, and older boards all parse and behave exactly as today.

Non-goals

  • No hard failure on member/team integrity. A dangling member reference, a binding pointing at a nonexistent group, a duplicate, or even a malformed member file never fails board loading, substrate validate, or a write. These surface as advisory warnings (see "Integrity is advisory"). The member layer is optional; breaking it must never break a project that is mostly (or entirely) using prose.
  • groups is not authorization. A member's groups is advisory — a hint for orchestration and UI, not an access restriction. There is no per-member write gating: Substrate has no authenticated principals, only the free-form created_by_agent actor label. Nothing about who may act in which group is enforced by this data. (The plain noun groups, not owns_/allowed_/restricted_to_, is itself the first signal that it is not a permission.)
  • No memory runtime behavior. Substrate stores the pointer (memory_dir) and nothing more. Whether a spawned agent reads that folder on start or writes learnings on exit is up to the agent — Substrate enforces no spawn ritual and no read/write of memory content. Reading-on-spawn / writing-on-exit is a possible fast-follow (or never); it is explicitly not in this task.
  • No memory content in JSON. The registry stores a folder path; the memory lives as files on disk (git-committed), never inline in the entity.
  • "Member" is not "agent" (the actor). A member is a persona/role identity; the existing created_by_agent / agent_name on writes is an actor audit tag on a specific mutation. These are different concepts and stay separate. Unifying them (binding a write's actor to a member id) is an explicit non-goal here — noted as a possible future direction, not part of this task.
  • No member write tools in v1. No create_member / update_member / board-binding MCP tools. Registry files and bindings are authored as code (hand-edited JSON), matching how groups/policies content is edited today. Write tooling is an explicit fast-follow.
  • No behavior change. Team data is inert: it does not gate transitions, fire messages, assign tasks, or substitute for agent_responsibility policies.
  • No change to whoami's payload shape. The bootstrap call stays a lean board summary; the team rides on get_board_substrate. (Any surface that does show team must resolve member identity from the registry — see below.)

Scope

Eight thin slices, no engine work:

  • Types. A Member interface (registry entity) and a TeamBinding interface (board reference) in src/core/types.ts; an optional team?: TeamBinding[] on Board and a members: Member[] on Substrate.
  • Registry loading + schema. Load .substrate/members/*.json into the Substrate (loader), with a MemberSchema and a TeamBindingSchema in src/substrate/schemas.ts. Missing directory ⇒ empty registry; a malformed member file is warned and skipped, not fatal (backward compat + "optional layer").
  • Cross-file integrity as warnings. In src/substrate/validator.ts (or the loader's diagnostics pass): a team[].member that doesn't resolve to a registry member, a groups id that isn't a group on the board, and duplicate member/id all produce advisory warnings routed through Substrate's existing warning channel — never an error, on either the load or write path.
  • Read-surface resolution. getBoardSubstrateHandler JOINs registry identity into the board's team so consumers get resolved members, not bare ids (an unresolved member is surfaced, not dropped — see UI). One handler feeds the MCP tool and the HTTP GET /api/boards/:id route → UI.
  • UI render. A "Team" card in the board-details disclosure grid resolving member id → name/description with group-assignment badges.
  • Migrate the two live boards. Extract the ## Team prose into per-member registry files + board bindings, remove the section from each description, bump each board's version. Reviewers ×2 becomes the first genuinely shared member — one registry file referenced by both boards.
  • Update the default scaffolding. The bundled web-delivery starter template gains a team binding plus default member registry files, and substrate init writes .substrate/members/*.json alongside the board. The bundled template stays strictly validated (see "Strict exception").
  • Sync the model docs. Update the docs that describe the board/team model so they match the structured members (mirrors how the release board treats doc verification).

Data structure — two layers

The design splits identity (project-level, shared) from assignment (board-level, specific).

Layer 1 — the member registry (identity, project-level)

One file per member at .substrate/members/<id>.json. This holds everything about who the member is, defined once: 

// .substrate/members/oversight.json
{
  "id": "oversight",                 // stable key; filename matches
  "name": "Oversight",               // display name
  "full_description": "Holds fidelity between what was specified and what shipped. Authors the spec up front, then returns at Review to check the implementation against the original goal, catching drift the builders can't see.",   // NEW: prose brief
  "traits": ["holds the original intent", "reads the diff against the spec"],
  "concerns": ["scope drift", "spec↔implementation fidelity"],
  "memory_dir": ".substrate/members/oversight/memory"   // NEW: pointer to a folder
}

// src/core/types.ts
export interface Member {
  id: string;                 // unique across the registry; matches filename
  name: string;               // display name
  full_description?: string;  // prose role brief — complements traits/concerns
  traits?: string[];          // short descriptors (chips / query)
  concerns?: string[];        // what the member watches for
  memory_dir?: string;        // path to a git-committed memory folder (pointer only)
}

full_description complements — does not replace — traits/concerns: the structured arrays drive chips and queries, the prose gives depth. memory_dir is a pointer to an on-disk folder (default convention .substrate/members/<id>/memory), committed to git so it is persistent, shared, and travels with the repo. The memory content never lives in the JSON. Only id and name are required.

Layer 2 — the board team binding (assignment, board-level)

Each board nests a thin team: a reference to a member plus the one thing that is genuinely board-specific — the group(s) that member is associated with on this board. 

// .substrate/boards/dev.json
"team": [
  { "member": "oversight", "groups": ["spec", "review"] },
  { "member": "builder",   "groups": ["build"] }
]

// src/core/types.ts
export interface TeamBinding {
  member: string;     // → Member.id in the registry; unresolved = warning, not error
  groups?: string[];  // group ids this member targets ON THIS BOARD;
                      // advisory (not a permission); [] / omitted = spans board
}
// on Board:
team?: TeamBinding[]; // optional → older boards without it still parse

groups lives on the binding, not the member, precisely because the same member is associated with different groups on different boards (Oversight targets spec+review on dev; it might target nothing, or a different group, on another board). Everything invariant about the member lives once in the registry; only the board-specific assignment lives on the board. The relationship is many-to-many in both directions: a member may target several groups, and a group may be targeted by several members (both Reviewers on review; Planner and Oversight both on spec).

Integrity is advisory — warnings, never errors

Because the member layer is fully optional and additive, every member↔board integrity problem is a non-blocking WARNING. It must never fail board loading, substrate validate, or any write. The board still works; Substrate just surfaces the discrepancy. A human is free to keep the roster in the board description prose and adopt the registry partially or not at all, so a mismatch is information, not an error.

Downgraded to warnings (from earlier drafts that called them errors):

  • Dangling member reference. A team[].member with no matching .substrate/members/<id>.json ⇒ warning; the board still loads (the binding renders as an unresolved member id in the UI).
  • Dangling group reference. A binding's groups id that isn't a group on that board ⇒ warning.
  • Malformed / unparseable member file. Bad JSON, missing required fields, or wrong types ⇒ warn + skip that member; the load still succeeds. One bad member file cannot break a project that is mostly using prose.
  • Duplicate member id / duplicate member in a board's team ⇒ warning.

These route through Substrate's existing non-blocking warning channel — the same advisory path substrate validate already uses for logical smells (e.g. a guard whose from_group === to_group), which prints ⚠ lines and still exits 0. No new warning mechanism is invented.

Strict exception — Substrate's own shipped defaults

One thing stays strict: the bundled default template. loadTemplateBoard / BoardSchema.parse must still fail loudly if a shipped default (the web-delivery template board + its default member files) is corrupt. That is a build-time invariant on Substrate's own artifacts, not a user-project runtime check. The distinction: user-project member files at runtime = lenient (warn / skip); Substrate's own shipped defaults at build/test time = strict. Loosening one does not loosen the other.

Semantics — advisory, not enforced

The team registry and bindings are descriptive. Substrate enforces nothing about who may act in which group. groups is a hint for orchestration and UI, not an access restriction: the orchestrator (a human, or a lead agent spawning members) decides the actual assignment at runtime. This mirrors how agent_responsibility policies are already documented as non-blocking suggestions. The advisory nature is carried by the neutral field name plus this documented contract — not encoded into the data shape (there is no suggested_groups, no binding_kind wrapper).

Where it lives — recommendation (reversed from v1)

Recommend: a project-level member registry (.substrate/members/<id>.json, one file per member) that boards reference by id, plus a thin per-board team binding. A member is a persistent identity that can span multiple boards and stages with shared memory (the Oversight case); that cannot be modeled by a roster line nested wholly inside one board's JSON. Splitting identity (shared, project-level) from assignment (specific, board-level) gives cross-board sharing, single-source identity, and a shared memory pointer for free, while keeping the board's binding minimal. Rejected alternative (v1): nesting the full roster in the board JSON — simpler, but structurally unable to express one identity across boards/stages, which is the whole point.

Member vs. actor — a deliberate distinction

A member is a persona: a named role identity with traits, concerns, and memory, defined in the registry. The existing actor label — created_by_agent on a task, agent_name on a write — is a free-form audit tag recording who performed a specific mutation. They answer different questions ("who is this role?" vs. "who made this edit?") and are intentionally kept separate in this task. A future unification (e.g. stamping a write's actor with a member id) is called out as a non-goal here so the two don't get conflated during implementation.

Memory pointer semantics

  • memory_dir is a path string to a folder, not content. Default convention: .substrate/members/<id>/memory, alongside the def file.
  • The folder is committed to git — persistent, shared across boards that reference the member, and it travels with the repo. A light markdown convention (e.g. append-only notes) is expected but not enforced.
  • Substrate does not read or write memory content. A spawned agent may choose to read it on start and append learnings on exit — that is up to the agent. This task ships the pointer only.

Relationship to agent_responsibility policies — unchanged

Two mechanisms describing "who works where" would be a smell, so the join is explicit and one-way: they are different jobs joined by group id, neither derived from the other, and both advisory (neither blocks).

member / team binding (new) agent_responsibility policy
Purpose Descriptive identity: who works here, their traits + concerns + memory. Operational nudge: a message to heed while a task is in a group.
When it's seen On read (get_board_substrate / UI) — orientation. At eval time, when a task's group_id matches when.
Effect None (inert metadata). Emits a suggestion (never blocks).
Recommend: coexist, joined by binding groups ↔ policy group ids; do not derive one from the other. A binding's groups points at the same group ids that agent_responsibility policies condition on (Reviewers target review; resp-review-gate fires in review), so the UI can cross-link a member to the responsibility message for a group it targets — by shared group id, with zero coupling in the data. Rejected: folding member metadata into policies — members are project-level identities, not per-group eval conditions.

Do members map to groups? — recommendation

Yes, optionally and many-to-many, via groups: string[] on the board binding. A member may target several groups on a board (Oversight → spec, review; Integrator → approval, merged), exactly one, or none (release-board Reviewers target no dedicated group). A group may be targeted by multiple members or none. No bijection required, and the association grants nothing (advisory). A groups id that isn't a real group on that board (archived allowed) is surfaced as a warning, not rejected.

How the UI renders it — recommendation

Recommend: a "Team" card in the existing board-details disclosure grid (BoardDetailsDisclosure in BoardDetail.tsx), beside "Field schema" and "Policies (n)". The card consumes the resolved team from the read surface: each row shows the member's name, its associated groups as assignment badges (id → group name), a traits line, and a concerns line; full_description can show as a tooltip or secondary line. An unresolved member (dangling ref) renders as the bare member id with a muted "unresolved" marker rather than disappearing. Absent/empty team renders a muted "No team declared" (matching "No policies."). Reuses existing Card/Badge components. Later, not v1: per-column assignment badges on the Kanban, a member detail view surfacing memory_dir.

Reusability & shared members

Reuse is native to this design: a member defined once in the registry is referenced by any board that binds it. Reviewers ×2 is the first genuinely shared member — a single .substrate/members/reviewers.json bound by both dev and release. A shared board template is a board JSON whose team references registry members; standing up a new board from it reuses the same identities (and their memory) rather than re-describing them.

Default scaffolding — new projects

Today substrate init --template web-delivery writes only a board file (src/cli/commands/init.ts → createBoardFile); the bundled template (src/cli/templates/web-delivery.board.ts, validated through loadTemplateBoard / BoardSchema.parse) carries no team. This task extends the default so a fresh project is coherent, not empty:

  • The web-delivery template gains a team binding whose members target the template's groups (Backlog / Spec / Plan / In Progress / Review / QA / Done), plus a set of default member registry files that ship with the template.
  • substrate init also writes those .substrate/members/*.json alongside the board file, under the same create/rollback window.
  • The template-validation gate (BoardSchema.parse / loadTemplateBoard, plus MemberSchema for the default member files) stays strict — a corrupt shipped default fails the build/test, distinct from the lenient runtime handling of user-project member files.
  • The examples/web-delivery source-of-truth copy (mirrored by the parse-equal test) gains the same members + binding so the bundled template and the example stay in lockstep.

Acceptance criteria

These are about the data structures + scaffolding + docs — registry files, bindings, advisory integrity, read resolution, UI, migration, the default template, and doc sync — not runtime memory behavior.

  • src/core/types.ts defines Member (id, name, full_description?, traits?, concerns?, memory_dir?) and TeamBinding (member, groups?); Board has an optional team?: TeamBinding[]; Substrate has members: Member[].
  • The loader reads .substrate/members/*.json into Substrate.members; a project with no members/ directory loads with an empty registry (backward compat, asserted by test).
  • Backward compatible: a board with no team key parses and renders as before; team and the registry are optional in the Zod schema.
  • Integrity problems are warnings, never failures. A dangling team[].member, a team[].groups id that isn't a group on the board, and duplicate member/id each produce an advisory warning and never fail board load, substrate validate, or any write (asserted by test — the board still loads and validate exits 0).
  • A malformed member file is warned-and-skipped, not fatal. A member file that is bad JSON, missing required fields, or wrong-typed is skipped with a warning; the rest of the substrate loads successfully (asserted by test).
  • Advisory, not enforced: a member's groups never gates a write or a transition — a write by any actor to any group succeeds regardless of the team data (asserted by test). No code path treats groups as a permission.
  • Resolution on read: get_board_substrate returns the team with member identity JOINed in (name, description, traits, concerns, memory_dir) plus the binding's groups; an unresolved member is surfaced (bare id + unresolved marker), not dropped; empty/absent team returns []. The HTTP GET /api/boards/:id response and the UI type carry the resolved shape.
  • The board detail UI shows a Team card: each member resolved to name + group-assignment name badges + traits + concerns; an unresolved member shows its id + marker; a board with no team shows the empty state without crashing.
  • Migration (two live boards): .substrate/members/ holds one file per role extracted from the prose; dev.json and release.json carry team bindings matching the prior ## Team content (no member, trait, or concern lost); Reviewers ×2 is a single shared registry file referenced by both boards; the ## Team section is removed from both descriptions (a test asserts no ## Team heading remains); both board versions are bumped; both load with zero integrity warnings.
  • Default scaffolding (new projects): substrate init --template web-delivery writes both the board and .substrate/members/*.json; the resulting substrate loads and validates with zero warnings (team bindings resolve); the web-delivery template + its examples/web-delivery mirror both carry the team; init.test.ts covers the members being written.
  • Shipped defaults stay strict: loadTemplateBoard / BoardSchema.parse (+ MemberSchema on the default member files) still fails loudly if a corrupt shipped default is introduced (asserted by test) — the lenient warn/skip behavior applies only to user-project member files at runtime.
  • Doc sync: skills/substrate/AUTHORING.md, skills/substrate/SKILL.md, prd.md, README.md, and docs/README.md describe the structured member registry + team binding (advisory + warning-not-error semantics included) rather than free prose; CLAUDE.md's "team as prose in the board description" line is flagged for a follow-up touch.
  • No transition/guard/responsibility/task-movement behavior changes (team data is inert); existing policy/guard suites pass unchanged; whoami's payload shape is unchanged.
  • Local gate green before Review: build + tsc + lint + format + full test suite pass locally.
