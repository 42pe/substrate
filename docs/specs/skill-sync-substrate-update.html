SPEC — Skill/binary sync

dev board · task aa08a050 · Draft — awaiting plan_approved · plan →

Problem

The globally-installed agent skill (~/.claude/skills/substrate) and the global substrate binary drift apart. There is no coupling between them: updating Substrate means rebuild + reinstall the binary (pnpm build then pnpm add -g …, per RELEASING.md "After a release") and separately cp -R skills/substrate ~/.claude/skills/substrate. The copy step is manual and easy to forget — it just bit us: four tool clusters shipped in the binary while the installed SKILL.md still advertised the old tool count until a human noticed. Every agent session in the meantime reads the stale skill and reasons from wrong facts (tool counts, command lists, conventions).

Two structural facts make this worse. (1) The skill source lives only in this repo (skills/substrate/); it is not in the npm package's files allowlist (package.json ships only ["dist", "README.md", "LICENSE", "CHANGELOG.md"]), so post-npm there is no repo to cp from. (2) Nothing stamps or checks the installed skill's version, so drift is silent — it is discovered by a human reading, not by a tool.

Goals

  • Ship the skill inside the package. The installed package carries its own canonical skill source, so a refresh has a source of truth even after npm publish (no repo checkout required).
  • A first-class refresh command. One command copies the packaged skill into ~/.claude/skills/substrate idempotently and version-stamped, so re-running is safe and drift is repairable.
  • Drift is detectable, not just fixable. A --check mode reports drift and exits non-zero (for CI / diagnose); substrate diagnose (and possibly whoami) surfaces a warning when the installed skill's stamped version ≠ the binary's BINARY_VERSION.
  • Release wiring. The "refresh the skill" step is documented alongside "reinstall the binary" in RELEASING.md and encoded in the release board's Released gate — so it is part of the ritual, not a thing to remember.

Non-goals

  • Not auto-installing the skill via an npm postinstall hook. Global postinstall scripts are fragile (silent failure, sandboxed installs, no TTY, permission surprises) and would write into ~/.claude without consent. An explicit command is the default posture. (Left as an open question below in case Diego disagrees.)
  • Not managing arbitrary third-party skills — this command owns exactly the substrate skill it ships.
  • Not a network fetch. Consistent with the rest of the CLI (templates are network-free; the agent does any cloning), the refresh copies from the local installed package only.
  • Not touching how the skill's content is authored (AUTHORING.md, the SKILL.md prose) — only how it is distributed, stamped, and synced.
  • Out of scope for v1 (decide later): whether the command also self-updates the binary (see open questions) — v1 scopes to the skill only.

Scope

  • Packaging. Add skills to the files allowlist in package.json (and update the mirror list in RELEASING.md's "Publishing to npm" note) so skills/substrate/ ships in the tarball.
  • Version stamp. A machine-readable stamp on the installed skill recording which BINARY_VERSION produced it, plus a runtime reader the binary uses to compare. (Frontmatter field vs sibling .version file — open question.)
  • New CLI command. substrate update (or install-skill — naming is an open question) that: resolves the packaged skill from its own install location; copies it to ~/.claude/skills/substrate; writes the version stamp; is idempotent. A --check flag reports drift and exits non-zero without writing. Wired into src/cli/index.ts dispatch, the HELP text, and the ALLOWED_FLAGS_BY_COMMAND allowlist in src/cli/args.ts.
  • Diagnostics. src/cli/commands/diagnose.ts gains a probe: read the installed skill's stamp, compare to BINARY_VERSION; a mismatch (or a missing skill) prints a ✗/advisory line. Possibly a hint in whoami (src/mcp/tools/read/whoami.ts).
  • Release ritual. RELEASING.md "After a release" adds the skill-refresh command; the release board's rel-gate-tagged policy on_failure_message in .substrate/boards/release.json changes from "reinstall the global binary" to "reinstall the binary and refresh the skill".

Acceptance criteria

  • npm pack / pnpm pack includes skills/substrate/SKILL.md and skills/substrate/AUTHORING.md in the tarball.
  • Running the new command with a stale or absent ~/.claude/skills/substrate leaves it byte-identical to the packaged skill and writes a stamp equal to BINARY_VERSION; running it again is a no-op (idempotent) and reports "already current".
  • The command resolves the packaged skill from the binary's own install path (works when invoked as a global install, not just from the repo).
  • <cmd> --check exits 0 when the installed stamp matches BINARY_VERSION and content matches; exits non-zero (with a clear message) when the skill is missing or stamped at a different version. It does not modify the filesystem.
  • substrate diagnose prints a skill-sync line and its exit code reflects a drift/missing state consistent with the existing problems convention.
  • An unknown flag on the new command is rejected via rejectUnknownFlags; --help lists the command with BINARY_VERSION in the header (existing behavior preserved).
  • RELEASING.md and .substrate/boards/release.json both instruct "refresh the skill" as part of the post-release / Released step.
  • The whole change validates locally (build + tsc + lint + format + test), since CI is billing-blocked.

Open questions (for Diego)

  • Command name & shape. substrate update vs substrate install-skill. update reads broader (implies it might also touch the binary); install-skill is precise about what it does. Recommendation: install-skill now (narrow, honest), reserve update for if/when it also self-updates the binary.

    Recommendation: substrate install-skill — as shipped. The build matched the tentative call.

    Rationale: the command is dispatched as install-skill in src/cli/index.ts, allowlisted as 'install-skill': new Set(['--check']) in src/cli/args.ts, and documented that way in the HELP text and in RELEASING.md. The name stayed honest: it only ever writes ~/.claude/skills/substrate, so update remains free for a verb that also touches the binary.

  • Explicit command vs npm postinstall. Spec assumes explicit-command-only (postinstall is a non-goal). Confirm — or do you want a best-effort postinstall that just prints "run substrate install-skill" rather than writing files?

    Recommendation: confirmed — explicit command only, and no postinstall at all (not even a printing one). This one the build settled by omission: package.json has no postinstall or prepare script.

    Rationale: a print-only hook buys a one-time line of install noise that is routinely swallowed by -g installs, while the two places that actually catch drift already exist — substrate diagnose's Skill section names the fix, and RELEASING.md's "After a release" block pairs substrate install-skill with the binary reinstall. Reopen only if, after the npm go-live, users who installed from the registry are found running a stale skill because they never saw the diagnose advisory.

  • How to stamp the version. (a) A frontmatter field in SKILL.md (e.g. x-substrate-version) — travels inside the file the agent reads, but mutates the canonical source and the frontmatter is agent-facing. (b) A sibling .version file written on install — keeps SKILL.md pristine and is trivial to read/compare, but is a second artifact that can be deleted independently. Recommendation: sibling .version (or .substrate-skill-version) file — simplest to read from diagnose/--check and does not touch the authored content.

    Recommendation: sibling .version file — as shipped. The build matched the tentative call: src/core/skill.ts exports SKILL_STAMP_FILE = '.version', and syncSkill writes BINARY_VERSION into <target>/.version after the copy. SKILL.md is never mutated.

    Rationale: the "deletable independently" downside is covered, not merely accepted. compareSkill falls back to a byte-for-byte file comparison, so a stamp that is missing or stale yields drift with the reason installed but unstamped — and diagnose deliberately reports that (and missing) as an advisory line rather than a counted problem, reserving the hard ✗ for a stamped-but-wrong-version skill (src/cli/commands/diagnose.ts). Confirmed in the field: a real machine reported "installed skill installed but unstamped — run 'substrate install-skill'", and after running it, "installed skill in sync (v0.7.0)" — so the legacy pre-stamping install upgrades gracefully instead of failing hard.

  • Does update also self-update the binary, or only the skill? v1 proposes skill-only. If you want a true "update everything" verb, that pulls in reinstalling the global binary (a pnpm add -g / npm reinstall), which is a bigger, environment-specific surface — recommend deferring.

    Recommendation: skill-only — hold the boundary. That is what shipped: syncSkill writes nothing outside ~/.claude/skills/substrate, and the binary reinstall stays a documented human step.

    Rationale: RELEASING.md's "After a release" runs pnpm add -g "$PWD/$(pnpm pack | tail -1)" then substrate install-skill — one line the release ritual owns, one line the binary owns. Self-updating would mean shelling out to whichever package manager installed us (pnpm/npm/volta/a tarball path), which the binary cannot know and cannot test. Keeping the installed binary current belongs with the npm publish / go-live work, not here. Reopen once Substrate is on npm and there are installs Diego does not perform himself — that is when a real substrate update (skill + npm i -g @diegoferreyra/substrate@latest) earns its keep.

  • Where does the binary read the packaged skill at runtime? Note: the CLI currently has no install-path resolution (import.meta.url/fileURLToPath appear nowhere in src/ — templates are compiled to JS modules, not read from disk). This command introduces the first "find my own package root" logic. Options: read from <pkgRoot>/skills/substrate (requires skills in files), or copy the skill into dist/ at build time and read from there. Recommendation captured in the plan.
