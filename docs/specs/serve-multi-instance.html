SPEC — Multi-instance serve

dev board · task serve-multi-instance · Draft — awaiting plan_approved · plan →

Problem

substrate serve binds a single pinned port and refuses to start when it's taken. In src/cli/commands/serve.ts the port is DEFAULT_PORT (7475, from src/http/server.ts) unless the test-only SUBSTRATE_PORT_OVERRIDE env var is set. When startHttpServer gets EADDRINUSE, serve throws SubstrateError.conflict("Port 7475 is already in use … Stop that process or change the port.") and exits. There is no --port flag (the header comment notes it's deferred to a future v1.x), so a second project's inspector cannot run while the first is up.

Working across several projects at once is a normal dogfooding case (Substrate tracks its own dev and release boards, and Diego runs it against other repos). Today that means stopping one inspector to look at another. Two serves should just coexist.

Goals

  • Coexistence (MVP). A second substrate serve in another project starts successfully even when 7475 is occupied, by auto-selecting a free port from a small range.
  • Discoverability. Each serve prints the actual URL it bound (it already logs Substrate running on http://localhost:<port>), and the chosen port is recorded so diagnose and the operator can find which port a project is on.
  • No new footguns. The PID-file lifecycle (single-owner-per-.substrate/, stale-PID reclaim, clean shutdown) keeps working; port bookkeeping is cleaned up on the same paths.
  • Stable-URL exploration. Assess a <project>.substrate.local scheme and recommend whether to implement now or defer, with rationale and setup cost.

Non-goals

  • Remote access. Serve stays bound to 127.0.0.1 only (per the origin/Host allowlist and startHttpServer's hardcoded hostname). Nothing here listens on 0.0.0.0.
  • A user-facing --port flag is not required by this task (may fall out of the work, but the acceptance bar is the automatic fallback, not manual port selection).
  • A central daemon / service manager that supervises all running serves.
  • Multiple serves against the same .substrate/. That stays forbidden — the single-PID-per-directory guard is intentional (one SQLite writer/owner per checkout).
  • Changing the default port away from 7475, or Windows-specific behavior beyond what identifyPortHolder already branches on.

Scope

MVP — free-port fallback (must ship). When the preferred port (7475) is taken, serve scans upward through a bounded range (e.g. 7475–7499) for the first free port and binds it. It prints/logs the chosen URL, writes the chosen port into the per-project bookkeeping next to the PID file, and diagnose reports the actual served port rather than only probing the fixed 7475. If the whole range is exhausted, fail with a clear, actionable error. This alone satisfies the acceptance criteria.

Stretch — <slug>.substrate.local stable URLs (explore; implement only if cheap). Give each project a stable hostname instead of a shifting port. Options to weigh (detailed in the plan): (a) /etc/hosts entries — needs sudo and is per-host manual; (b) a loopback DNS resolver — dnsmasq answering *.substrate.local → 127.0.0.1 plus a one-time macOS /etc/resolver/substrate.local file (wildcard, no per-project sudo, but still leaves the port problem — a name alone doesn't route to the right port); (c) a small always-on reverse proxy that maps slug → port using the per-project bookkeeping and listens on a single fixed port. The spec's position: the .local name only becomes genuinely useful when paired with a proxy that routes name→port; otherwise it's a cosmetic alias over a port that still changes. Recommend accordingly.

Acceptance criteria

  • With a server already bound to 7475, running substrate serve in a second project starts without error, selects a free port in-range, and prints its URL.
  • Two projects can serve simultaneously; each prints its own URL; neither throws EADDRINUSE.
  • A single serve with 7475 free still binds 7475 (no behavior change for the common case).
  • The chosen port is recorded per project and surfaced by diagnose (operator can answer "which port is this project on?" without lsof).
  • Range exhaustion yields a clear error naming the range that was tried.
  • Shutdown (SIGINT/SIGTERM) and stale-PID reclaim still clean up both the PID file and the new port record.
  • The .local domain is written up as a recommendation in the plan; implemented if it lands cheaply, otherwise deferred with explicit rationale.

Open questions (for Diego)

  • Preferred-port-then-scan? Keep 7475 as the always-first-tried default and only scan 7476…7499 on conflict (proposed), so the first/primary project keeps the memorable URL — agreed?
    Recommendation: yes — and this is what shipped. portCandidates(DEFAULT_PORT, PORT_RANGE_START, PORT_RANGE_END) in src/shared/process.ts returns 7475 first and then 7475–7499 minus the preferred port, and serve.ts walks that list by attempting a real bind (no pre-probe, so racing serves can't pick the same port). Honest caveat: 7475 goes to whichever serve starts first, not to a designated primary — there is no per-project affinity, so restarting the main project while another holds 7475 moves it. If pinning ever matters, the answer is the deferred --port flag, not a stickiness heuristic.
  • Where to persist the chosen port? Options: (a) extend the existing PID file to hold pid + port (e.g. two lines or JSON at .substrate/substrate.pid); (b) a sibling .substrate/substrate.port file; (c) fold both into a small .substrate/serve.json runtime file. All stay gitignored. Preference? (Leaning toward a single JSON runtime file for extensibility, migrating the current bare-PID format.)
    Recommendation: keep what shipped — a separate serve.json with the PID file untouched. This diverges from the spec's lean. .substrate/substrate.pid is still a bare PID; .substrate/serve.json (src/shared/serve-runtime.ts, paths().serveRuntime) is an additive { pid, port, started_at } record written after a successful bind and cleared on every teardown path. That is better than the proposed migration: the ownership guarantee is the writeFile(…, { flag: 'wx' }) exclusive create, and folding it into JSON would couple atomic ownership to a serializer and force a format migration on every existing checkout for no gain. The split also lets discovery data be absent or corrupt (readServeRuntime returns null) while the lock stays strict.
  • Range + size. Is 7475–7499 (25 slots) the right window, or wider/narrower?
    Recommendation: keep 7475–7499 as shipped. A slot is one project's inspector on one machine, so 25 is already far above the realistic ceiling, and exhaustion fails with a message naming the range and the count. Widening later is a two-constant edit in src/http/server.ts with no format or compatibility consequence — the CORS/Host allowlist is rebuilt per candidate port — so there is no cost to starting narrow.
  • Is .local worth the setup? A no-sudo wildcard needs dnsmasq + a resolver file (one-time, but still an install), and to actually be useful needs a reverse proxy to map slug→port. Do you want stable URLs enough to run an always-on proxy, or is "serve prints its URL + diagnose lists it" good enough for now?
    Recommendation: don't build it — defer indefinitely. The wildcard-DNS half is cosmetic on its own (a name that still doesn't route to the right port), and the half that makes it useful is a name→port reverse proxy — an always-on daemon, which this spec's own non-goals already rule out. "Serve prints its URL + diagnose lists it" is good enough and now real: diagnose reports serving on port N (pid M) straight from serve.json. Weighing it against the roadmap idea Shared substrate pointer, which reframed the adjacent pain as several working copies pointing at one local DB: that direction reduces the number of concurrent serves rather than multiplying them, so stable hostnames would be solving memorability, not divergence. Trigger to revisit: if an always-on Substrate process ships for an independent reason (the v1.x HTTP MCP transport is the live candidate), name→port routing becomes an add-on to a daemon that already exists rather than a new one — reopen then, and not before.
  • Slug source. If we do .local, the slug would derive from config.project_name (itself defaulted from basename(cwd) at init) — collisions across two same-named checkouts are possible. Slug from project_id (UUID) instead, or name-with-dedup?
    Recommendation: build no slug while question 4 stands. If it reopens: name-with-dedup, keyed internally on project_id. A UUID hostname is unmemorable, which defeats the only reason to want .local at all — so config.project_id should be the stable identity in the bookkeeping while config.project_name supplies the visible slug, with a numeric suffix on collision between two same-named checkouts. Trigger: this question only becomes live if question 4's proxy trigger fires; there is nothing to decide until then.
