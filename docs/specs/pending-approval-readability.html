SPEC — Pending-approval readability

dev board · task c607b04e (pending-approval-readability) · Draft — awaiting plan_approved · plan →

Problem

substrate pending-approval is the human's cross-board report of every task waiting on them — an autonomous agent hit a transition_guard requiring a human_only field it can't set, so the task sits until the human runs substrate approve. Today the command (src/cli/commands/pending-approval.ts) prints a nested bulleted list: per task a title + id line, a free-text "waiting on you to set … to move X → Y" line, and one run: substrate approve … line per field. That is three-to-four lines per task with no vertical alignment, so with more than a couple of pending items the human can't scan "what's blocked and what do I type" at a glance. There is no machine-readable form either — anyone scripting off it must scrape prose.

Goals

  • Scannable at a glance. Default output is an aligned table (Diego's locked decision) so the eye can run down columns — one row per pending task.
  • Color helps, safely. Color is applied only on an interactive TTY; output is plain bytes when piped, redirected, or NO_COLOR is set. Color never carries meaning that the plain text loses.
  • Copy-paste unblock. Each row still surfaces the exact substrate approve <id> <field> command, verbatim and pipe-safe.
  • Machine-readable. A --json flag emits the structured aggregate, at parity with the list_pending_approvals MCP tool.
  • Grouped + counted. Rows are grouped by board with a leading total count, preserving today's cross-board framing.
  • No new dependency. Table layout and color come from a tiny in-repo ANSI/pad helper — no chalk, no table lib.

Non-goals

  • No change to what counts as pending — the derivation stays in src/policy/pending-approval.ts and the shared aggregate listPendingApprovals (src/operations/list-pending-approvals.ts). This is a presentation change.
  • No interactivity — no paging, no cursor/keyboard, no "approve from here". It stays a one-shot print. substrate approve remains the sole write path.
  • No new columns beyond the ask's set (Task / Move / Awaiting / Approve). No sorting/filtering flags beyond --json.
  • No change to the MCP tool or the HTTP /api/pending-approvals route contract (the colorized list fallback, if ever needed, is a CLI-only render).
  • No wrapping engine for arbitrarily wide content — long fields are truncated with an ellipsis, not reflowed across lines.

Scope

One CLI command's output plus its flag plumbing:

  • Table renderer (default). Columns: Task (title truncated + short id), Move (current group → target group), Awaiting (the human_only field(s)), Approve (the exact command). Grouped by board with a board sub-header; a leading N task(s) pending human approval in <project> count line. Columns are width-aligned to their widest visible cell; long titles are truncated to fit; narrow terminals (process.stdout.columns) shrink the flexible Task column first.
  • Color, TTY-gated. Enabled only when process.stdout.isTTY and !process.env.NO_COLOR and not --json. Suggested roles: board header bold, the approve command in a distinct color, the awaiting field emphasized. A tiny ANSI helper (new module) provides the escapes; alignment math measures visible width (excludes escapes).
  • Plain fallback. When color is off, identical layout with zero escape bytes — the table still aligns.
  • Empty state. Unchanged text for the no-pending case; under --json, still valid JSON (count: 0, items: []).
  • Flag plumbing. --json added to the pending-approval allowlist in src/cli/args.ts and dispatched in src/cli/index.ts; HELP text updated to mention the table + --json.

Acceptance criteria

  • With ≥2 pending tasks across ≥1 board, default output is an aligned table: a count line, then per board a header and one row per task; the Task/Move/Awaiting/Approve columns line up vertically.
  • Every row contains a verbatim, runnable substrate approve <task_id> <field> (one per awaiting field), byte-identical to what substrate approve expects.
  • Piped / redirected / NO_COLOR output contains no ANSI escape bytes (no \x1b[), yet stays column-aligned. (Asserted by test.)
  • On a TTY without NO_COLOR, output contains color escapes; stripping the escapes yields exactly the plain-mode layout.
  • --json prints valid JSON that deep-equals the listPendingApprovals result (same object the MCP tool returns) — parity, never colorized, and honored even on a TTY. (Asserted by test.)
  • The existing empty-state message is preserved (human mode); --json empty state is { "count": 0, "items": [] }-shaped valid JSON.
  • Long titles are truncated with an ellipsis so no row exceeds the terminal width; the short id remains fully visible.
  • substrate pending-approval --bogus still fails via rejectUnknownFlags; --json is accepted.
  • Existing tests in src/cli/commands/pending-approval.test.ts still pass (adjusted to the new layout) and new tests cover the plain/NO_COLOR and --json criteria above.

Open questions (for Diego)

1. Group labels in the Move column. The shared aggregate carries group ids (group_id, gate.to_group), and today's output prints those raw ids (e.g. build → review). Show ids (zero risk, no contract change) or resolve to human group names? Names are friendlier but need either a CLI-side board lookup or an additive group_name/to_group_name on the shared item (which the MCP tool + UI would also gain). Default proposed: keep ids for this task; enrich later if it grates.
Recommendation — ids shipped; revisit with an additive to_group_name.

What shipped: raw ids. src/cli/commands/pending-approval.ts builds the cell as `${it.group_id} → ${it.gate.to_group}`, so the Move column reads ideas → spec.

Rationale: On this repo's own dev board the ids barely resemble the names the human sees — ideas is "Ready to Start", spec is "Spec & Plan", approval is "Pending Review and Approval" — so the row names a column that isn't on screen anywhere else. The aggregate already resolves board_name beside board_id, and src/http/routes/api/board-columns.ts already emits group_name, so an additive group_name/to_group_name on PendingApprovalItem follows an established pattern rather than inventing one. The wider blast radius is a benefit here, not a cost: the UI has the same wart today — ui/src/routes/TaskDetail.tsx renders "to move to {approval.gate?.to_group}" in the pending-approval tooltip, i.e. the raw id. Ship it as a follow-up task: add both fields (keep the ids in --json for scripts), render names in human output.

2. Truncation budget. When process.stdout.columns is undefined (non-TTY) or very narrow (<~80), what's the fallback width — assume 80, or don't truncate at all when width is unknown? Proposed: assume 80 when unknown, shrink Task column to a floor (~24 chars) before truncating id/command.
Recommendation — keep exactly what shipped (assume 80, floor the title at 24).

What shipped: the proposal, verbatim — DEFAULT_COLUMNS = 80 and TITLE_FLOOR = 24 in src/cli/commands/pending-approval.ts, with flexWidth() (src/cli/table.ts) shrinking only the title column.

Rationale: Right call, and the interesting part is the third case the question didn't ask about: when even the 24-char floor overflows, flexWidth returns the floor and lets the row exceed the width rather than clipping the later columns — which is the only behavior compatible with the "verbatim, runnable substrate approve …" acceptance criterion. A wrapped or clipped command would be worse than a wrapped line. Covered by the columns: 60 case in src/cli/commands/pending-approval.test.ts.

3. Color palette. Any preference beyond "board header bold + approve-command colored + awaiting emphasized"? (e.g. dim the short id, yellow the awaiting field.) Proposed defaults live in the plan; easy to tune.
Recommendation — keep the three shipped roles; don't dim the short id.

What shipped: bold board name, yellow awaiting field(s), cyan approve command (src/cli/commands/pending-approval.ts), from the four SGR wrappers in src/cli/color.ts.

Rationale: Three roles is the right ceiling — the strip-back test (stripAnsi(colored) === plain) is what keeps color decorative, and every extra role is another thing that must survive it for no scanning gain. Skip the "dim the short id" idea specifically: the id is the thing the human copies, so de-emphasizing it works against the command's whole purpose. Loose end worth naming: dim is exported and tested but has no caller — fine as a spare, but it is dead code today.

4. Fallback list. The locked decision keeps a colorized aligned list documented only as a lean fallback if the table proves too heavy. Ship the table alone now and leave the list unbuilt (documented in the plan), correct?
Recommendation — yes: table only, leave the list unbuilt permanently.

What shipped: one renderer. renderPendingApprovals is the sole render path in src/cli/commands/pending-approval.ts; no list fallback exists anywhere in src/cli/.

Rationale: Right call — the plain (NO_COLOR/piped) path is already the lean rendering the fallback was meant to provide, byte-identical to the colorized one minus escapes, so a second renderer would be a second layout to keep in sync against a need that hasn't materialized. If the table ever does prove too heavy, the honest fix is narrower columns, not a parallel renderer.
