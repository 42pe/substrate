SPEC — Board name in top bar

dev board · task board-name-top-bar · Draft — awaiting plan_approved · plan →

Problem

The read-only inspector (ui/, served at localhost:7475) has a single global header (ui/src/routes/Layout.tsx → Shell) that never changes between routes: a fixed Substrate wordmark, the primary nav (Overview / Boards / Activity), and a theme toggle. Once you click into a board or a task, nothing in that persistent chrome tells you which board you are looking at or which project you are in. You have to read it off the page <h1> (present on BoardDetail, but on TaskDetail the only board affordance is a raw board_id back-link — ← main, not the human name) or infer it from the URL. The bare route reads poorly and the board name — which the data already carries — is never surfaced in a stable spot.

The data is already there: getProject() returns project_name, getBoard(id) returns board.name, and every task from getTask(id) carries a board_id (ui/src/lib/api.ts). This is purely a UI-surfacing task — no schema or API change.

Goals

  • A persistent app header that always shows the project name (linking to Overview /).
  • When on a board route (/boards/:id) or a task route (/tasks/:id), the header also shows the active board's human name (not its id), and clicking it navigates to that board.
  • The header updates correctly on client-side navigation (board → task → another board → Overview) with no stale name.
  • Works across all three deep routes: board (kanban), board (list), and task detail.
  • Stays read-only, responsive, and theme-aware; does not crowd or displace the existing live-polling indicator (LiveIndicator), which lives in page body sections, not the header.

Non-goals

  • No board switcher/dropdown in the header — just a name (and its link). A picker is a separate follow-up.
  • No new server endpoint or aggregate route; reuse the existing getProject / getBoard / getTask GETs.
  • No schema change — boards already carry name, projects already carry project_name.
  • No change to the page-level <h1> on BoardDetail/TaskDetail, to the nav items, or to the live indicator's placement/behavior.
  • No breadcrumb of group/task title in the header (out of scope; the board name is the ask).

Scope

  • Touched surface: the shared header inside ui/src/routes/Layout.tsx (the Shell component), plus a small new header component/hook and its unit test. All four routes render through Layout's <Outlet/> (see ui/src/main.tsx), so a header change applies everywhere at once.
  • Header contents, left→right: Substrate wordmark (unchanged, → /) · project name (→ /) · when on a board/task route, a separator + the active board name (→ that board). Primary nav and the theme toggle stay where they are.
  • Data sourcing: project name from getProject(). Active board name resolved from the route: on /boards/:id directly via getBoard(id); on /tasks/:id via getTask(id) → board_id → getBoard(board_id) (the acknowledged extra fetch). Details of reuse-vs-refetch are a plan/implementation decision — see the plan.

Acceptance criteria

  • On Overview (/), Boards (/boards), and Activity (/activity): the header shows the project name linking to Overview; no board segment is shown.
  • On /boards/:id (both ?view=kanban and ?view=list): the header shows project · <board name>, and the board name links to that board.
  • On /tasks/:id: the header shows project · <board name> for the task's own board (resolved from board_id), with the name — not the raw id.
  • Navigating between routes updates the board segment immediately; leaving a board/task route clears it. No stale board name.
  • The header is responsive (wraps/truncates gracefully on narrow widths) and does not overlap or crowd the live indicator.
  • While the board name is loading or fails to resolve, the header degrades gracefully (see open questions) — it never shows a raw error or a jarring layout jump.
  • Tests updated: a new component test for the header (project always shown; board name shown on board/task routes, absent elsewhere; updates on navigation), and the Playwright smoke (tests/smoke/ui.spec.ts) asserts the header board name (Roadmap) is visible on /boards/main and /tasks/t1.

Open questions (for Diego)

  • Exact header contents per route. Proposed: wordmark + project · board (project always a link to Overview). Is the Substrate wordmark + project name redundant — should the wordmark be dropped in favor of just the project name, or kept as the app identity? And on the plain routes (Overview/Boards/Activity), show project name only, or nothing extra?
  • Separator/format. Project · Board vs a breadcrumb chevron (Project ⟩ Board) vs two distinct pills. Any preference to match the existing badge/muted-text vocabulary?
  • Task route board fetch. Acceptable to do the extra getBoard(board_id) on task detail (simplest, decoupled), or should we thread the already-fetched board data up to the header to avoid it (more coupling, slight flash on first paint)? See plan Risks.
  • Loading/failure behavior. While the board name resolves (or if getBoard 404s/errors), should the header (a) show nothing for the board segment, (b) fall back to showing the board id, or (c) show a subtle skeleton? Preference to avoid layout shift.
  • Mobile behavior. At the narrowest widths the header already wraps (nav + toggle). Should the board name truncate with an ellipsis on one line, wrap to a second line, or be hidden below a breakpoint (kept only as the page <h1>)?
  • Archived boards. Should the header board segment carry the archived marker (as BoardDetail's <h1> does), or stay name-only to keep the bar slim?
