SPEC — submit_feedback MCP tool

dev board · task 06d6dd55 (submit-feedback) · Draft v1 — awaiting plan_approved · plan →

Problem

Agents (and their humans) hit rough edges while using Substrate — a confusing tool schema, a policy that fired unexpectedly, a docs gap — but there is no in-flow way to capture that feedback. It evaporates with the session. Filing an issue means the agent leaves its runtime, finds the repo, and hand-writes an issue; most of the time it simply never happens. Substrate needs a one-call tool that turns "the agent noticed a problem" into "the maintainer can see it," without breaking Substrate's no accounts, no cloud, no telemetry promise.

Goals

  • One call, ready-to-file. A single MCP tool, submit_feedback, takes a title + body and hands back a prefilled GitHub issues/new URL for 42pe/substrate that a human clicks to actually submit.
  • Tokenless, zero network egress. The tool never contacts the GitHub API, needs no credentials, stores nothing, and emits no event. The server stays a pure local string-builder — the privacy promise is preserved by construction.
  • Consistent tool shape. A read-style tool that returns plain data with no ok envelope, mirroring whoami and reverse_captcha, living under src/mcp/tools/read/.
  • Triage-friendly. The issue title carries the Substrate Feedback: tag prefix and a feedback label; the body is version-stamped with BINARY_VERSION so a maintainer knows which release the feedback came from.
  • Bounded & deterministic. Input length is capped in the schema so the assembled URL stays practical; the same inputs always produce the same URL (pure function).

Non-goals

  • No API submission. The tool does not POST to GitHub, does not create the issue, and does not authenticate. A human completes the submission by clicking.
  • Not configurable. The target repo is hardcoded to 42pe/substrate (this is feedback about Substrate itself, so every install points upstream). No per-project override in v1.
  • No persistence. No board write, no task, no comment, no task_events row — the call leaves no trace in the substrate.
  • No category input. A bug/idea/docs selector mapping to labels is deferred (see resolved question 4). v1 inputs are title, body, and optional agent_name only.
  • No environment capture. The body footer does not include OS, node version, or any host detail — that would erode the no-telemetry ethos (resolved question 3).

Scope

  • New tool handler. src/mcp/tools/read/submit-feedback.ts — a pure handler plus a registerSubmitFeedback function, following the whoami/reverse_captcha template (shape object, zod schema, wrapToolHandler).
  • Registry wiring. Register the tool in src/mcp/registry.ts among the read tools (natural placement next to reverse_captcha).
  • Version stamp. Read BINARY_VERSION from src/core/version.ts for the body footer (single source of truth — same import whoami uses).
  • Tool-surface test. Add submit_feedback to the asserted tools/list array in tests/integration/mcp-bootstrap-flow.test.ts (surface grows 31 → 32).
  • Unit test. src/mcp/tools/read/submit-feedback.test.ts — URL assembly, title prefix, version stamp, encoding, optional attribution, and schema caps.
  • Docs. Add submit_feedback to the substrate skill's tool reference (the 31 → 32 count) and mention it in README / AGENTS where the tool surface is described.

Exact tool I/O shape

Inputs (zod shape)

Field Type Notes
title z.string().min(1).max(120) Required. Short summary. The Substrate Feedback: prefix is added by the tool, so the cap applies to the author-supplied portion.
body z.string().min(1).max(4096) Required. The detail. Cap keeps the encoded URL within GitHub's practical prefill budget for ASCII text.
agent_name z.string().min(1).max(80).optional() Optional. Woven into the body footer for attribution when present.

Over-limit input fails at the schema layer and is surfaced as a schema_violation envelope by wrapToolHandler — the message states the cap. No silent truncation (resolved question 1).

Output

Plain read data — a single result variant, no ok field (so wrapToolHandler marks it isError: false, exactly as whoami/reverse_captcha do): 

{
  "result": "feedback_url",
  "url": "https://github.com/42pe/substrate/issues/new?title=...&body=...&labels=feedback",
  "issue_title": "Substrate Feedback: <title>",
  "repo": "42pe/substrate",
  "instructions": "Open this URL in a browser and click 'Submit new issue' to file it. Nothing was sent automatically."
}

URL & body construction

  • issue_title = `Substrate Feedback: ${title}`.
  • Body = the author's body, then a minimal footer: 
    <body>

---
Filed via Substrate v<BINARY_VERSION>
Agent: <agent_name>        ← line present only when agent_name is supplied
  • url = https://github.com/42pe/substrate/issues/new?title=${enc(issue_title)}&body=${enc(body)}&labels=feedback, where enc is encodeURIComponent.
  • repo is the constant '42pe/substrate'.

Resolved open questions

1. URL length cap → schema caps, hard reject, no truncation. title ≤ 120 chars, body ≤ 4096 chars, enforced by .max() in the zod schema. Over-limit input returns a schema_violation whose message names the cap; the agent shortens and retries. We reject rather than truncate so no feedback is silently lost. For typical ASCII bodies the encoded URL stays comfortably under GitHub's ~8 KB prefill guideline; pathological high-entropy/multibyte bodies that inflate under percent-encoding are an accepted v1 edge (documented in the plan's risks) — GitHub still renders the form.
2. feedback label → always sent; create the label once upstream. The tool always includes labels=feedback. A one-time maintainer step creates the feedback label on 42pe/substrate (documented as a prerequisite in the plan). If the label is momentarily absent, GitHub shows a cosmetic "label doesn't exist" banner but still lets the human submit — it is not a hard failure, so the tool does not depend on repo state to function. The Substrate Feedback: title prefix is the primary, always-present tag.
3. Body footer → version stamp + optional attribution only. The footer carries only Filed via Substrate v<BINARY_VERSION> and, when supplied, an Agent: <name> line. No OS, no node version, no host fingerprint — consistent with Substrate's no-telemetry promise.
4. Optional category → out of scope for v1. A bug/idea/docs selector mapping to additional labels is scope creep for the first cut. v1 ships title, body, agent_name. Revisit as a follow-up if triage wants finer routing.

Acceptance criteria

  • Calling submit_feedback with a valid title and body returns { result: 'feedback_url', url, issue_title, repo, instructions } and writes nothing (no DB row, no event, no comment).
  • issue_title equals Substrate Feedback: <title> and the title= query param decodes to that same prefixed string.
  • url targets https://github.com/42pe/substrate/issues/new, includes labels=feedback, and its title/body params are encodeURIComponent-encoded (special characters — &, #, newlines, spaces — round-trip correctly via decodeURIComponent).
  • The decoded body ends with a footer containing Substrate v<BINARY_VERSION>, and the exact version string tracks src/core/version.ts (no hardcoded literal).
  • When agent_name is supplied, the decoded body footer contains an Agent: <name> line; when omitted, no such line appears.
  • repo is exactly '42pe/substrate'.
  • A title > 120 chars or body > 4096 chars yields a schema_violation (not a thrown error, not a truncated URL); an empty title or body is likewise rejected.
  • The response carries no ok field and isError is false.
  • tools/list includes submit_feedback and the asserted surface in mcp-bootstrap-flow.test.ts is 32 entries.
  • The substrate skill's tool reference lists submit_feedback and its count reads 32.
