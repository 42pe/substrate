SPEC — Unapprove / revoke a human approval

dev board · task a3c7177f (unapprove-revoke-approval) · Draft v1 — awaiting plan_approved · plan →

Problem

substrate approve <task_id> <field> [value] is the human channel that sets a human_only gate field (B3) — plan_approved, idea_approved, diego_approved, release_approved. Once set, a transition_guard that requires it lets the gated move through. But there is no clean way to undo a mistaken approval. Our gates check op: exists (occasionally eq true), and the existing merge path only sets values — running substrate approve <task> <field> false writes false but the key still exists, so an exists guard still passes and the gate stays open. To truly re-gate, the field must be deleted from the task's custom_data, and there is no first-class command that deletes it through the human channel.

Substrate already has the deletion primitive internally: the MCP update_task handler treats a null value as "delete this key" and writes the whole custom_data blob with the key removed (src/mcp/tools/write/update-task.ts). But an agent is forbidden from touching a human_only field there (that's what makes the gate real), and there is no human-side command that performs the same delete. So a human who approves by mistake is stuck.

Goals

  • Human-only revoke. A first-class substrate unapprove <task_id> <field> that deletes the field from the task's custom_data, so a gate that requires it re-blocks — for both exists and eq true guards.
  • Symmetric with approve. Same "is this a human_only field?" guard, same OS-user actor stamped human:<user> in the event log, same optimistic version bump. An agent can no more revoke than it can approve.
  • Clear confirmation. Prints old value → cleared, and the new version — the mirror image of what approve prints.
  • Safe to re-run. Revoking a field that is already unset is a friendly no-op, not an error — but a field that is not a human_only field is still refused.
  • Honest about side effects. If the task already moved past the gate on the mistaken approval, warn that it is now stranded — unapprove never moves the task.

Non-goals

  • No auto-move. unapprove clears the field and nothing else. It never moves the task back to an earlier group — that is a separate, human-driven step (see Resolved question 2).
  • No new deletion primitive in the repo. This reuses the existing merged-blob write path; it does not add a tombstone, an unset column, or a new updateTask capability.
  • No MCP tool. Revoke is a human action, CLI-only, symmetric with approve (which is also CLI-only). No unapprove MCP write tool is added, and no MCP read tool changes. (See Resolved question 5.)
  • No approve --revoke flag. Command shape is a distinct verb (Resolved question 1).
  • No change to the gate model. Guards, operators, and the pending-approval derivation are untouched; revoke only removes a value the gate reads.

Scope

One new CLI command plus its flag/dispatch plumbing and tests:

  • New command src/cli/commands/unapprove.ts, mirroring src/cli/commands/approve.ts. It resolves the task's board, enforces the human_only guard, deletes the field from a merged copy of custom_data, writes via the existing OCC updateTask, appends an updated event stamped human:<user>, and prints a confirmation.
  • Field deletion uses the same mechanism as the MCP handler: build merged = { ...task.custom_data }, delete merged[field], and hand the full blob to updateTask (which writes JSON.stringify(merged) wholesale). No repo change. validateFieldSchema skips absent/undefined keys, so the write validates cleanly.
  • Stranded warning — when the task's current group is the to_group of an active transition_guard on its board that requires the revoked field, print a warning that the task now sits past that gate and must be moved back manually. Reuses the same field↔gate mapping helpers the pending-approval derivation already uses (src/policy/pending-approval.ts).
  • Plumbing — add unapprove to the flag allowlist in src/cli/args.ts (empty set, like approve), dispatch it in src/cli/index.ts with the same <task_id> <field> positional parse, and add a HELP line.

Command shape & behavior

substrate unapprove <task_id> <field>
  • Field resolution + human-only guard. Load the task's board; look up board.field_schema.task[field]. If it is not human_only === true, throw schema_violation with the same framing as approve ("'<field>' is not a human-only field … unapprove clears human-only gate fields"). This runs before the idempotency check, so a typo or a non-gate field always errors rather than silently no-op'ing.
  • Idempotent no-op when already unset. If the field passes the human_only check but is absent from custom_data (nothing to revoke), print a friendly line ("Nothing to revoke: <field> is not set on task <id>."), exit 0, no version bump, no event. Mirrors the repo's idempotent archive/unarchive semantics (a no-op emits no event, bumps no version).
  • Delete + write. Otherwise, build merged = { ...custom_data }, delete merged[field], run validateFieldSchema (absent key is always allowed), and call updateTask(tx, id, version, { custom_data: merged }, now) under the existing optimistic-concurrency read-check-write in a single transaction.
  • Actor stamping. Append an updated event with actor_agent_name: 'human:<os-user>' and changes.before.custom_data / changes.after.custom_data reflecting the removal — symmetric with approve's event.
  • Confirmation. Revoked: cleared <field> (was <old-value>) on task <id> (as human:<user>, version <n>).
  • Stranded warning (conditional, second line). If the task's current group is the to_group of a guard requiring <field>, additionally print a Warning: line noting the task now sits past that gate with the field cleared, and that unapprove does not move tasks — move it back on the board (web UI) or have an agent move it. No fabricated substrate move command (none exists — see Resolved question 2).
  • Not-found. A missing task_id throws not_found (via getTask), same as approve.

Example output

$ substrate unapprove a3c7177f plan_approved
Revoked: cleared plan_approved (was true) on task a3c7177f (as human:diego, version 7).

$ substrate unapprove a3c7177f plan_approved            # already cleared
Nothing to revoke: plan_approved is not set on task a3c7177f.

$ substrate unapprove a3c7177f severity                 # not a human_only field
Error: Field 'severity' is not a human-only field on board 'dev'. …

$ substrate unapprove 12ab34cd diego_approved           # task already merged past the gate
Revoked: cleared diego_approved (was true) on task 12ab34cd (as human:diego, version 12).
Warning: task 12ab34cd is in group 'merged', past the gate that required diego_approved.
         unapprove does not move tasks — move it back on the board if that was a mistake.

Resolved open questions

1. Command shape — unapprove verb (not approve --revoke). approve's grammar is positional — approve <id> <field> [value] — where the third positional is the value; a --revoke flag there would fight the "set a value" identity of the command and be easy to miss. A distinct verb is self-documenting, discoverable in --help and the HELP list, and reads as the exact inverse. Decision: substrate unapprove <task_id> <field> (no value argument — revoke has nothing to set).
2. Task already past the gate — warn, never move. Auto-moving a task backwards is a bigger, riskier action (which earlier group? what if several gates were crossed?) and would couple revoke to move semantics. Decision: unapprove only clears the field; it prints a warning when the task's current group is the to_group of a guard that required the field. Note on accuracy: there is no substrate move CLI command in this repo (moves happen via the web UI or an agent's update_task), so the warning must not fabricate one — it names the group + gate and tells the human to move it back on the board. Detection is scoped to a direct to_group match (no multi-hop reachability) to stay simple; multi-hop stranding is a documented non-goal for v1.
3. Stranding is allowed, with a warning. Revoke never refuses on the grounds that it would leave a task in a later group. It always clears the field and (when applicable) warns. The human, not the tool, decides whether to move the task back.
4. Not-set is a friendly no-op, not an error. Once the human_only guard has passed (so the field name is a real gate field), a field that simply isn't set has nothing to revoke — treat it as an idempotent success with a clear message, no version bump, no event. This keeps re-runs and scripts safe. A wrong field (not human_only) still errors with schema_violation, because that check runs first — so typos surface loudly while genuine re-runs are quiet.
5. CLI-only; no MCP surface. Like approve, revoke is a human action performed by a person at a terminal, stamped as the OS user. Exposing it over MCP would hand an agent a revoke capability and muddy the "agents can't touch human_only fields" guarantee, for no benefit. Decision: CLI-only. No unapprove MCP write tool; no change to list_pending_approvals or any read tool.

Acceptance criteria

  • Re-gates an exists guard. Given a task whose move is gated on require: [{ field: task.custom_data.plan_approved, op: exists }]: after approve the gate passes; after unapprove <id> plan_approved, check_transition for that move returns allowed: false again. (Asserted by test.)
  • Re-gates an eq true guard. Same round-trip for a guard whose leaf is { op: eq, value: true } on a human_only boolean — unapprove deletes the key, so eq true evaluates false and the gate blocks. (Asserted by test — both operator shapes covered.)
  • Deletes the key (not sets false). After unapprove, the field is absent from the task's custom_data (not present with value false).
  • Human actor recorded. The revocation appends an updated event with actor_agent_name matching /^human:/, with before.custom_data containing the field and after.custom_data lacking it.
  • Version bump + confirmation. The task version increments by 1, and stdout reports the old value, "cleared", and the new version.
  • Non-human_only field refused. unapprove <id> severity (a non-gate field) throws schema_violation and changes nothing. (Asserted by test.)
  • Idempotent no-op when unset. Running unapprove on a human_only field that is not currently set exits 0 with the "nothing to revoke" message, bumps no version, and appends no event. (Asserted by test.)
  • Not-found. A missing task id throws not_found.
  • Stranded warning, no move. When the task's current group is the to_group of a guard requiring the field, unapprove prints a warning and the task's group_id is unchanged. (Asserted by test.)
  • Full round-trip. A single test drives approve → gate passes → unapprove → gate blocked again → approve → gate passes, proving symmetry end-to-end.
  • Plumbing. substrate unapprove is dispatched; an unknown flag is rejected via rejectUnknownFlags; missing positional args print a usage line; the HELP block documents the command.
