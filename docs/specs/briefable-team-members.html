SPEC — Briefable team members

dev board · task 15d45ca7 (briefable-team-members) · Draft v1 — awaiting plan_approved · plan →

Roadmap authority: d475f273 “More structured team definition” (roadmap_approved 2026-09-06). This spec decides the technical questions that plan explicitly hands to the Dev board; it does not re-open its scope.

Problem

v0.7.0 (task 9a5af742) made the team queryable: a member is a first-class registry entity at .substrate/members/<id>.json, bound to a board by a TeamBinding, and resolved into the orientation payload by get_board_substrate. It did not make the team usable.

A member record answers “who is on this board?”. It does not answer the question an orchestrating agent actually asks at the moment it spawns a sub-agent: “what do I say to this member?” The record holds identity — full_description, traits, concerns — all written in the third person, all describing the member rather than charging it. So every brief is composed by hand, and the hand-written part is always the same three things the record cannot express: the charge, the hand-back, and the rules that void the output.

We have this from our own dogfood: the brief that produced the roadmap plan behind this task quoted product-shaper.json’s full_description almost verbatim, then appended a mandate (“shape this one idea”), a deliverable (“five sections, in the description, no files”), and guardrails (“product level only; you cannot set the human gate”). The registry supplied identity; a human supplied everything that made the identity actionable.

The consequence is Substrate’s signature failure mode, one layer up: the process moved out of CLAUDE.md into boards, groups and policies, but the operating instructions for each character stayed in chat history. The policy layer already tells an agent what is expected at a place on the board. Nothing tells an orchestrator what is expected of a member.

The second gap: a shared member cannot be sharpened locally

reviewers.json is bound by two boards (dev → review, release → the whole board). Its shared prose currently ends: 

"full_description": "Two independent reviewers with distinct adversarial lenses — e.g. (a)
 correctness & security, (b) product, tests & docs. Skeptical; verify claims against the
 code; try to break it. Shared across the dev and release boards; ON RELEASE THE LENSES ARE
 TUNED TO DOCS-VS-CODE AND RELEASE MECHANICS."

(Emphasis added — that last clause is the problem.)

That trailing clause is a shared record apologising for a board-specific fact, and the same smuggling shows in concerns, which mixes dev-review items (“re-review the fix round”) with release items (“a release that misstates what changed”). There is nowhere to put a board-local sharpening, so it gets folded into the shared record — where every other board then has to read past it.

Goals

  • An orchestrator can assemble a working brief by quoting the board. No invention, no reconstruction from chat history. The test is mechanical: the three hand-written parts of a real brief must each have a named slot to be quoted from.
  • A human reading the Team card learns something the name didn’t already tell them — what the member is charged with, what it hands back, what voids its output.
  • It rides the orientation payload. The briefing arrives in get_board_substrate, the call an orchestrator already makes once per board. No second lookup, no new tool — the plan is explicit that a brief behind an extra fetch will not be fetched.
  • A board may sharpen a shared member locally without forking it. Additive and descriptive, exactly as groups is today: the registry keeps what is invariant about the member, the binding keeps what is true only on that board.
  • Content authored for all 8 existing members (builder, doc-auditor, integrator, planner, product-shaper, release-engineer, reviewers, validator) plus the 4 bundled web-delivery members. Per the plan this is most of the actual cost.
  • Brevity is enforced as a warning. The plan’s own stated failure mode is “not a second CLAUDE.md”, and its stated mitigation is brevity. That mitigation gets a mechanism (advisory only) rather than a hope.
  • Fully additive and backward compatible. Every new field is optional; a member with none of them, a board with no team, and a project with no registry all behave exactly as today.

Non-goals

Carried literally from the approved plan. These are cuts, not omissions.

  • No spawn mechanics. No model, no effort or token hints, no tool allowlists, no permissions, no stored prompt text. That is harness configuration — runtime-specific, fast-rotting, and inside the standing “no agent runtime, no model hosting, no prompt management” non-goal. This boundary is the load-bearing decision of the plan: .claude/agents/*.md owns runtime mechanics; Substrate owns the runtime-neutral, in-repo, process half. Two records, one boundary, no overlap.
  • Substrate never launches anything. No spawn API, no execution, no orchestration. It hands over words.
  • Still advisory, still optional. No per-member gating, no authorization, no write permissions derived from a member. Every integrity problem stays a warning; nothing a member says can block a write or a transition.
  • No typed, enumerated or weighted traits. guardrails is string[] of free prose, like traits/concerns. Nothing in the product reasons over the values.
  • No member↔policy references. The two layers stay separate.
  • No handoff graph. Group order plus the binding already implies it.
  • No memory format or discipline. memory_dir stays an unread pointer (roadmap idea afad022e owns that question). None of the eight memory_dir folders exists on disk today; this task does not change that.
  • No member write tools and no UI editing. Members and bindings stay authored as JSON in git. update_board has no team input today and gains none here.
  • No change to whoami’s payload. The bootstrap call stays a lean board summary; the briefing rides get_board_substrate.
  • Not a second CLAUDE.md. If a member’s briefing grows past a few lines it has failed.

Scoped out of this task (not plan non-goals — deliberate deferrals)

  • substrate explain does not render the team at all today — renderSubstrateHtml destructures only { config, boards } (src/explain/render.ts:11) and emits zero member output. The roadmap plan names explain as an adjacent surface, but adding a team section to it is a separate feature (rendering the roster, not briefing it) and would be new scope regardless of this task. Out. Flagged for a follow-on idea.
  • Templates carrying members — dev task ba3b8c01; see “Relationship to ba3b8c01” below.

Scope

Seven slices. Slices 1–4 are the mechanism (small); slice 5 is the content (most of the cost); slices 6–7 are docs and tests.

  • 1. A Brief type, used in two places — on Member (the registry brief) and on TeamBinding (the board-local sharpening). src/core/types.ts.
  • 2. Schemas. BriefSchema in src/substrate/schemas.ts; brief added as an optional key to MemberSchema and TeamBindingSchema.
  • 3. Read-surface pass-through. ResolvedTeamMember gains a board-local brief; the registry brief already flows for free because get-board-substrate.ts splices the whole Member object by reference. Mirror the type in ui/src/lib/api.ts (a hand-maintained duplicate). Update the get_board_substrate tool description so an agent knows the field exists and how to compose it.
  • 4. Advisory length lint in src/substrate/validator.ts, routed through the existing substrate.warnings channel, surfaced by substrate validate and counted by substrate diagnose. Warning only; exit code unchanged.
  • 5. Author the content. All 8 live members, the board-local sharpening for reviewers on release (and the de-smuggling of the shared record), and the 4 bundled web-delivery members in both mirror locations.
  • 6. UI. Render the brief in the existing Team card (ui/src/routes/BoardDetail.tsx, TeamCard).
  • 7. Docs. skills/substrate/AUTHORING.md §“Team members”, and the README/PRD lines that describe the member record.

Data structure — one Brief, two homes

The three slots

The plan leaves “one field or three, and what they are called” to this spec. The answer is three named slots, in one nested object, using the plan’s own words: 

// src/core/types.ts

/**
 * The briefing half of a member record: what an orchestrator quotes when it
 * brings this member in. DESCRIPTIVE — like everything else in the member
 * layer, nothing here gates a write, a move, or a permission. Substrate never
 * launches anything; it hands over words.
 *
 * Deliberately NOT a place for spawn mechanics (model, tools, permissions,
 * prompt text) — that is harness config and stays in the runtime's own agent
 * definitions. See the spec's non-goals.
 */
export interface Brief {
  /** The charge, stated so the member can act on it: an imperative sentence,
   *  not a third-person description. "Turn one raw idea into a shaped plan." */
  mandate?: string;
  /** What it hands back, and where that lands. */
  deliverable?: string;
  /** The few things that make this member's output worthless when violated. */
  guardrails?: string[];
}

// on Member (registry — invariant across every board that binds it):
brief?: Brief;

// on TeamBinding (board-local sharpening — additive, never a replacement):
brief?: Brief;
Three slots, not one blob. A single brief: string would be cheaper to add and would fail the plan’s own test twice over. Named slots make quoting mechanical (an orchestrator reads three keys, not a paragraph it must parse), make omission visible (an empty deliverable is a hole you can see in the Team card), and give the length lint something to bound per-slot. A free paragraph is precisely the shape that grows into a second CLAUDE.md — the plan’s named failure mode.
Nested under brief, not flat on the member. The member record already has flat identity fields (full_description, traits, concerns). Nesting keeps the two halves visually and structurally distinct — identity vs. call sheet — which is the exact conceptual split the plan draws. It also lets one BriefSchema serve both homes, so registry and binding can never drift apart, and makes “compose the brief” a two-object operation rather than a six-key one.

How the three slots relate to the three that already exist

Field Answers Voice
full_description Who is this member? Third person, descriptive
traits How does it work? Third person, chips
concerns What does it watch for in the work? A lens it applies outward
brief.mandate What is it charged with, this time? Imperative, addressed to the member
brief.deliverable What must it hand back, and where? Imperative
brief.guardrails What voids its own output? Constraints on itself
concerns vs guardrails is the one line that will blur if it is not stated. Concerns are the lens the member applies to the work it is looking at (Reviewers: “never rubber-stamp”). Guardrails are constraints on the member’s own output, whose violation makes that output worthless (Reviewers: “never grade your own work — a self-review is not a review”). Some of today’s concerns entries are really guardrails and move during slice 5; the authoring pass must not leave the same sentence in both fields.

Composition: side by side, never merged

A binding’s brief is additional context for this board. Substrate performs no string concatenation and no key-level override: the resolved payload returns the registry brief (inside member) and the board brief (beside it) as two separate objects, and the consumer composes. This is the same posture groups already has — the binding carries the board-specific part, the registry carries the invariant part, and joining them is the reader’s job. 

// src/mcp/tools/read/get-board-substrate.ts
export type ResolvedTeamMember =
  | { unresolved: false; member: Member; groups: string[]; brief?: Brief }
  | { unresolved: true;  member: { id: string }; groups: string[]; brief?: Brief };

The documented reading rule, which goes in the tool description and in AUTHORING.md:

Both briefs apply. Where both fill the same slot, the board’s is the sharper one for this board — it narrows the registry’s general charge; it does not contradict it. Where only one fills a slot, that one is the whole answer for that slot.

A brief survives on an unresolved binding. The binding is what carries it, so a board-local brief renders even when the referenced member id has no registry file — consistent with the existing rule that a dangling reference is surfaced, not dropped.

Worked example — the reviewers case the plan names

// .substrate/members/reviewers.json — the shared record, with the
// board-specific apology REMOVED from full_description and concerns
{
  "id": "reviewers",
  "name": "Reviewers ×2",
  "full_description": "Two independent reviewers with distinct adversarial lenses. Skeptical;
    verify claims against the code; try to break it.",
  "traits": ["distinct adversarial lenses", "skeptical",
             "verifies claims against the code", "tries to break it"],
  "concerns": ["never rubber-stamp", "catch real blockers"],
  "brief": {
    "mandate": "Review this change independently, with a lens distinct from the other reviewer's.
      Try to break it; verify every claim against the code rather than the report.",
    "deliverable": "A verdict — APPROVE or BLOCK — with each blocking finding as a
      file:line claim someone else can check.",
    "guardrails": [
      "Never grade your own work; a self-review is not a review.",
      "Re-review the fix round — an approval on round one does not carry.",
      "A finding you cannot point at in the code is not a finding."
    ]
  },
  "memory_dir": ".substrate/members/reviewers/memory"
}

// .substrate/boards/release.json — the board-local sharpening
"team": [
  { "member": "reviewers", "groups": [], "brief": {
      "mandate": "Review the RELEASE: the docs against the code, and the publish/tag path
        against RELEASING.md.",
      "guardrails": ["A release whose CHANGELOG misstates what changed is a BLOCK, not a nit."]
  } }
]

// .substrate/boards/dev.json — needs no sharpening; the registry brief IS the dev lens
"team": [ { "member": "reviewers", "groups": ["review"] } ]

The shared record stops apologising, the release board says its own thing, and the dev board needs no entry at all. That is the “additive and descriptive, exactly like groups” the plan asked for.

Validation & the brevity lint

Schema

BriefSchema is a plain z.object (zod’s default strip mode, matching every other schema in the file — no .strict(), no .passthrough()). All three keys optional; strings .min(1); guardrails an array of .min(1) strings.

Today these fields are silently dropped. Because MemberSchema is a plain z.object, a brief written into a member file right now parses cleanly and is stripped before it reaches Member — no warning, no error. That is why this is a code change and not a documentation change, and it is worth stating in the tests.

Failure posture is unchanged and inherited: a member file whose brief fails the schema is warned and skipped like any other malformed member file (loader.ts), because the whole member layer is optional. Substrate’s own bundled web-delivery members stay on the strict MemberSchema.parse path in loadTemplateMembers — a malformed shipped default is a build failure, as today.

The brevity lint

The plan states the failure mode (“not a second CLAUDE.md”) and the mitigation (“brevity”). Give the mitigation a mechanism, at the advisory tier the whole layer already uses:

Check Threshold Effect
brief.mandate length > 280 characters warning
brief.deliverable length > 280 characters warning
each brief.guardrails[] entry > 200 characters warning
brief.guardrails count > 5 entries warning

Message format matches the existing validator strings exactly:

Member 'reviewers' brief.mandate is 412 characters — a mandate should be a charge, not a
  document (soft limit 280). Advisory.
Board 'release' team member 'reviewers' brief.guardrails has 8 entries — keep the few that
  make the output worthless when violated (soft limit 5). Advisory.

Pushed through substrate.warnings, so it appears in substrate validate (exit code stays 0), is counted by substrate diagnose’s members/ line, and reaches update_board’s log-only teamCtx.warn sink. It never refuses a write and never fails a load.

Why a lint at all, when the plan asked for no new mechanism? Because the plan names brevity as the mitigation for its own stated drift risk, and an unmeasured mitigation is a hope. It costs one pure function and four constants, it cannot break anything (warning-only, on a channel that already exists and already prints), and it is the cheapest way to notice the kill signal early. Thresholds are soft and named constants — easy to retune from dogfood. If Diego reads this as scope creep, cut slice 4; nothing else depends on it.

Relationship to ba3b8c01 (templates can’t carry members)

The card asks whether the two should be specced together. No — spec them separately; they are a shape change and a delivery bug. This task changes what a member record can say. ba3b8c01 fixes substrate add producing dangling member refs because an external template carries boards but no members (src/cli/commands/add.ts, init.ts:69-70). Neither blocks the other: briefs land in the registry and in board bindings whether or not add can carry them, and fixing add is correct whether or not briefs exist.

But the coupling is real and runs one way. The roadmap plan’s §2 argues that the biggest downstream multiplier is templates — “a template that ships a board plus a briefed team is a workflow you can run.” That claim is false while ba3b8c01 is open: a shared template cannot carry members at all, so it certainly cannot carry their briefs. Recommendation: land ba3b8c01 before or alongside this, and do not cite the template multiplier as delivered value until it is. The bundled web-delivery template is unaffected — it ships members through loadTemplateMembers, a different path.

Acceptance criteria

  • AC1. Brief exists in src/core/types.ts with optional mandate, deliverable, guardrails, and is referenced by an optional brief?: Brief on both Member and TeamBinding.
  • AC2. MemberSchema and TeamBindingSchema accept and retain brief. A regression test proves the pre-change behaviour is gone: a member JSON carrying brief round-trips instead of being silently stripped.
  • AC3. A member file with no brief, a binding with no brief, a board with no team, and a project with no members/ all load exactly as before, with no new warnings.
  • AC4. get_board_substrate returns the registry brief inside member and the board-local brief as a sibling brief, unmerged. A test asserts that binding a member from two boards with different board briefs yields an identical member object and different sibling briefs — the same shape the existing shared-reviewers test asserts for groups.
  • AC5. A board-local brief on a binding whose member id does not resolve is still returned, alongside unresolved: true.
  • AC6. An over-long mandate/deliverable, an over-long guardrail, and a >5-entry guardrails list each produce exactly one advisory warning naming the member (and the board, for a binding brief). substrate validate prints them and exits 0; loadSubstrate does not throw; a write is not refused.
  • AC7. A brief that fails BriefSchema in a user-project member file warns and skips that file, exactly like any other malformed member file. The same brief in a bundled template member throws from loadTemplateMembers.
  • AC8. All 8 live members have a mandate, a deliverable, and at least one guardrail; no sentence appears in both concerns and guardrails on the same member; reviewers.json no longer contains a board-specific clause; the release binding for reviewers carries the release lens. substrate validate on the live .substrate/ reports zero warnings.
  • AC9. All 4 bundled web-delivery members carry a brief, in both src/cli/templates/web-delivery.members.ts and examples/web-delivery/.substrate/members/*.json, and the existing parse-equal drift test passes.
  • AC10. The Team card renders mandate, deliverable and guardrails for a resolved member, renders a board-local brief when present, and renders nothing extra when absent. Existing empty-state (Team (0) / No team declared.) and unresolved rendering are unchanged.
  • AC11. The get_board_substrate tool description states that team[].member.brief and team[].brief both apply, that the board’s is the sharper one for that board, and that the brief is descriptive — it confers no permission and launches nothing.
  • AC12. whoami’s payload is byte-identical to before.
  • AC13. skills/substrate/AUTHORING.md documents the three slots, the composition rule, the concerns-vs-guardrails line, and the brevity soft limits.

Open questions (for Diego)

Q1 — Keep the brevity lint (slice 4)? It is the one thing in this spec the roadmap plan did not ask for. It exists because the plan named brevity as the mitigation for its own drift risk. Recommendation: keep — it is warning-only, ~40 lines, and independently cuttable.
Q2 — Soft limits: 280 / 200 / 5. Chosen so a mandate is one or two sentences and guardrails stay a short list. Retunable in one constant block. Push back if they feel wrong.
Q3 — guardrails as prose strings, not an enum. Follows the plan’s “no typed/enumerated traits” non-goal literally. Confirming because it is the one place where a controlled vocabulary would have been tempting.
Q4 — Sequencing against ba3b8c01. Recommendation above is “land ba3b8c01 first or alongside”. If you would rather ship briefs now and fix templates later, that is fine — the only cost is that the template multiplier stays an unearned claim until it lands.
