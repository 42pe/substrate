Dependency — this is specced against typed document references

The evidence panel shows “the task body and its linked spec/plan” at the moment of sign-off. Built on spec_doc — a free-text markdown field nothing validates — it would render unverified links at exactly the instant the product asks a human to be rigorous. Diego approved the typed-document-references plan (1aafe9e5) to fix that.

That spec is now written (docs/specs/typed-document-references.html), and this one is specced against the design it landed on, not against spec_doc. The concrete coupling:

  • Documents are a field_schema field type — { type: 'document_refs', roles: [...] } — with values in custom_data shaped [{ role, path }], repo-relative and enforced at write time.
  • Resolution is advisory and read-time. The shared contract this feature consumes is GET /api/tasks/:id/documents, which returns { role, path, exists }[]. This spec adds no resolution logic of its own.
  • Dead references are shown, marked dead, and not hyperlinked — they are evidence about the state of the evidence, which is exactly what a person clearing a gate needs to see.
  • Build order: 69cd3660 lands first. If it slips, raise it — do not silently fall back to spec_doc. A panel that renders unverified links is the failure this dependency exists to prevent. (Degrading gracefully is still correct: a board that declares no document_refs field simply shows no documents section.)

Problem

Human approval gates are Substrate’s most differentiating feature, and the only part of the product that asks the human to leave the product to use it. Clearing one means reading the agent’s report, switching to a terminal, copying a UUID, and typing substrate approve <uuid> <field>. The agent knows exactly which task and which field are blocked — it just said so — and then hands over a transcription job.

The cost is not the typing; it is latency, and what latency does to the decision:

  • Approvals go stale before they are made. One sitting on 2026-07-14 cleared seven in a row. Six were decided long after the moment the agent explained its work. The friction did not buy scrutiny; it bought a batch of rubber stamps at the end of the day. Friction is not rigour.
  • The whole board stops. In a single-approver product, every human gate is a hard stop; approval latency is the pipeline’s dominant queue time.
  • It is the worst first impression of the best feature. A new user’s first encounter with the human-only gate is “the tool printed a UUID and told me to retype it”.

The state is already computed and already displayed. list_pending_approvals, substrate pending-approval and GET /api/pending-approvals all share one aggregate (src/operations/list-pending-approvals.ts) that knows precisely which task, which gate, and which fields await a human. The per-task flag is already on the task detail page as a “pending approval” pill (ui/src/routes/TaskDetail.tsx:39-47). The product surfaces the state everywhere and can act on it nowhere. The B3 code comment already names the intended human channel as “substrate approve / the UI”; the UI half was never built.

The governing principle

You cannot approve from anywhere you cannot also see what you are approving.

The click is not the feature — the evidence is. A gate is only meaningful if a human formed a judgment. Making the judgment one click away from a confident agent summary, with nothing else on screen, converts the one gate that is not a confession step into one that is. So the deciding surface must show what Substrate itself knows, independent of the agent’s narration. Shipping the button without the evidence would only make rubber-stamping faster, and should not ship at all.

Goals

  • A pending-approvals view in the inspector — everything awaiting a human across every board. The UI counterpart of substrate pending-approval.
  • A per-task approval review on the task detail: which gate, which transition it unblocks, the guard’s own guidance message, the task body, the task’s checked document references, recent comments, recent history — then the Approve control, attached to that evidence.
  • Revocation in the same surface. substrate unapprove exists; recoverability is what earns the right to make approval one click, not a nice-to-have.
  • Human attribution in the trail — matching the CLI’s human:<user> stamp, and recording the channel.
  • Fast one-at-a-time throughput — land on the next item with its evidence already there. This is the ergonomics people mistake for wanting batch.
  • No new network exposure. Whatever serve already is.
  • Generic over boards. Anything a substrate declares human_only gets this. No special-casing diego_approved, plan_approved or roadmap_approved.

Non-goals

Carried literally from the approved plan.

  • Batch approval / select-all / “approve these five”. The strongest cut in the plan. Batch is the rubber-stamping mechanism — one click for N judgments — and it directly violates the governing principle. The seven-in-a-row was a symptom of latency; fix the latency and the demand dissolves. Out.
  • Approving from any view that does not show the evidence — including a button on a kanban card or a queue row. Open the item, then approve.
  • No Claude widget in this feature. It couples the flagship human gate to one vendor’s client, and it sits underneath the agent’s own account of its own work — the worst possible venue for an evidence problem. Deferred to a separate, conditional idea; if it ever ships it is a shortcut into this surface, not a parallel path with less context.
  • No other UI write. No editing tasks, comments, boards, groups, fields or policies from the inspector. Substrate stays authored as code.
  • No remote, hosted or mobile approval; no auth, accounts, multiple approvers, roles or delegation. All excluded by the product’s shape (localhost, single-user, no auth).
  • No notifications of any kind. The pending view is something you go and look at.
  • No turning team / members into a permission or approver model.
  • No change to how gates are evaluated, and no new agent capability. That is the point.

The read-only property, restated more precisely

The inspector’s read-only rule exists to stop the UI becoming an authoring surface that competes with substrate-as-code, and to keep the agent’s data path singular. Approving threatens neither — it is not authoring, and it is not work state. So the property is sharpened, not broken:

The inspector never writes work state and never authors substrate. It hosts exactly one action: the human-only approval channel — the one write that has no agent equivalent by design.

Two write channels, cleanly split:

Channel May touch May never touch
Agent / MCP Everything except human_only fields Any human_only field (B3)
Human (CLI + inspector) Only human_only fields Everything else

That is more explainable than “read-only, except”, and it draws a line that resists the slide — which is itself named as a hard non-goal above.

What B3 actually guarantees — and the bar a new channel must clear

An honest restatement, because the plan corrects an overclaim here and the correction changes the answer. What B3 guarantees: an agent’s MCP write tools refuse to set a human_only field, and update_board refuses to un-protect one. That is a guarantee about Substrate’s agent-facing API. It is not a guarantee that no agent can ever cause an approval — an agent with shell access can run substrate approve today. What stops that is the harness’s permission prompts and the human watching, not Substrate.

The real, defensible property: approval requires an action on a channel outside Substrate’s agent-facing API, on the human’s own machine, that the human controls. A new channel must match the CLI’s trust boundary. It does not need to clear a higher one, and claiming it does would be dishonest about what we already ship.

The inspector meets that bar: the human opens it in their own browser, on their own machine, over localhost only; the agent does not render it, does not frame it, and cannot cause a click.

(The README and the B3 code comment currently overclaim — “structurally cannot self-clear” reads as airtight. That correction is dev task d3f38afb, independent of this feature and out of scope here.)

Scope

1. The write path — one shared operation, two human channels

substrate approve and substrate unapprove today duplicate the same pipeline inline in src/cli/commands/: resolve board → assert the field is human_only → merge → OCC write → append an updated event stamped human:<os-user>. Extract it to src/operations/approval.ts, following the list-pending-approvals.ts precedent, and have both CLI commands and both HTTP routes call it.

This is the security-relevant part of the design. The human_only assertion is what makes the HTTP channel safe, and it must exist in exactly one place. Two copies would be two chances to diverge — on the one check the whole feature rests on. 
POST   /api/tasks/:id/approvals            { field, value? }   → set a human_only field
DELETE /api/tasks/:id/approvals/:field                         → revoke it

The operation refuses, with schema_violation, any field the task’s board does not declare human_only: true — the same refusal substrate approve gives today, in the same words.

2. Preserving the “HTTP cannot reach the write path” invariant

ApiDeps is Pick<ToolDeps, 'client' | 'config' | 'loadSubstrate'> — deliberately no root, “so the HTTP surface structurally can’t reach the substrate-write root”. That invariant is preserved exactly: an approval writes a task row in SQLite (client) and reads the board from substrate-as-code (loadSubstrate). It never writes a .substrate/*.json file, so it never needs root. Do not widen ApiDeps.

What does change is the comment above registerApiRoutes, which currently reads “Reads only — NO write route is ever registered, so the API cannot mutate state regardless of method.” That sentence stops being true and must be replaced with the sharpened property, not left to contradict the code.

3. Origin handling on the write routes

originAllowlist allows a request whose Origin header is absent — “curl, server-to-server, MCP stdio: allow”. For reads that is fine. For the approval routes, require an Origin that is present and in the allowlist.

Honestly stated: this does not stop an agent with shell access — nothing can, and substrate approve already exists for exactly that human. Per the corrected bar above, matching the CLI boundary is the requirement, and a no-Origin curl from the local machine is that boundary. Requiring Origin costs nothing, removes an accidental difference between the two channels, and keeps browser CSRF closed. It is hygiene, not a guarantee, and should be described that way.

4. The pending-approvals view — /approvals

  • A new route, backed by the existing GET /api/pending-approvals. No new aggregate.
  • Grouped by board: task title, short id, group → to_group, awaiting field(s).
  • Each row is a link and nothing else. No Approve button, no checkbox, no select-all. Opening the item is the only way through — that is the non-goal made structural.
  • A count in the app header/nav so the queue is discoverable without polling a page.

5. The per-task approval review

An Approval tab on the task detail, alongside Details / Comments / Events. It appears when the task is pending approval or when any human_only field is currently set (so revocation is always reachable). Contents, in order:

Block Source
What you are clearing — the gate policy name + id, the transition it unblocks (group → to_group), and the awaiting field(s) GET /api/tasks/:id/approval (exists)
The guard’s own guidance — the policy’s on_failure_message, verbatim GET /api/boards/:id policies
The task body, rendered GET /api/tasks/:id (exists)
Documents — the task’s typed references with resolution state; dead ones marked and not linked GET /api/tasks/:id/documents — from 69cd3660
Recent comments (last 5, newest first) GET /api/tasks/:id/comments (exists)
Recent history (last 10) with actor and time GET /api/tasks/:id/history (exists)
Then the Approve control, per awaiting field The new write route
And the currently-set human_only fields, each with Revoke custom_data ∩ human_only schema keys

Every read but one already exists. The control is below the evidence, never beside the title, never in a sticky bar — you scroll past what you are approving to reach the button. That ordering is the governing principle expressed as layout.

6. Revocation

Same surface, same operation in reverse: the field is deleted from custom_data (an absent key reads undefined, so an exists/eq true guard re-blocks). Reuse unapprove’s stranded-task detection — if the task already advanced past the gate on the mistaken approval, say so, and say that revoking does not move it back. Never moves a task.

7. Attribution

The actor stamp is identical to the CLI’s — human:<os-user> from os.userInfo(), since the serve process runs as that human. Uniform actor strings keep substrate activity’s by_actor honest and the trail readable. The channel is recorded in the event’s changes as channel: 'inspector' | 'cli', and the CLI is backfilled to stamp 'cli' in the same change so the field is never ambiguous by omission.

8. Throughput without batch

After a successful approval the panel shows the result and offers “Next pending →”, navigating to the next item with its evidence loaded. Walking a queue of seven stays seven decisions; it just stops costing seven context switches. This is the whole answer to the batch demand.

Acceptance criteria

  • AC1. src/operations/approval.ts is the single implementation of approve and revoke. substrate approve, substrate unapprove and both HTTP routes call it; no second copy of the human_only assertion exists in the codebase.
  • AC2. The HTTP routes refuse any field not declared human_only: true on that task’s board, with schema_violation — tested for a plain field, an undeclared field, and a human_only field belonging to a different board.
  • AC3. ApiDeps still has no root. A test asserts the type, and the stale “NO write route is ever registered” comment is replaced with the sharpened property.
  • AC4. The write routes reject a request with an absent or non-allowlisted Origin; read routes are unaffected.
  • AC5. A successful approval writes the field, bumps the task version, and appends an updated event with actor human:<user> and changes.channel === 'inspector'. The CLI path stamps the same actor with channel: 'cli'.
  • AC6. Revocation deletes the key, and a guard requiring it re-blocks afterwards — asserted through check_transition, not by inspection.
  • AC7. Revoking a field the task has already advanced past reports the stranded condition and does not move the task.
  • AC8. /approvals lists every pending item across every board, grouped by board, and contains no approve affordance — no button, no checkbox, no select-all anywhere in the DOM.
  • AC9. The Approval tab renders all seven evidence blocks, with the control below them. A task with no pending gate and no set human_only field shows no tab.
  • AC10. Document references render with resolution state; a dead reference is visibly marked and is not a link. A board declaring no document_refs field renders no documents block and no error.
  • AC11. Nothing special-cases a field name. A synthetic board with a differently-named human_only field gets the full surface.
  • AC12. No MCP tool is added or changed; agent write tools still refuse human_only fields; update_board still refuses to un-protect one; gate evaluation is untouched.
  • AC13. The server still binds 127.0.0.1 only; no new port, no new header, no auth.
  • AC14. An OCC conflict (the task changed under the reviewer) surfaces as a readable “this task changed — re-read before approving” state, never a silent overwrite.
  • AC15. “Next pending →” advances one item at a time with evidence loaded, and never approves anything by itself.

Open questions (for Diego)

Q1 — Requiring Origin on the write routes makes the HTTP channel marginally stricter than the CLI (a no-Origin local curl is refused). The plan says match the CLI boundary, not exceed it. Recommendation: keep it — it is free, and the difference is an accident of the read-only middleware rather than a deliberate parity.
Q2 — Same actor string, channel in changes. The alternative is a distinct actor like human:diego (inspector), which would make the channel visible in every activity table for free — at the cost of two spellings of the same person in by_actor. Recommendation: uniform actor, channel in the payload.
Q3 — Evidence depth: 5 comments, 10 events. Enough to see the recent argument without turning the panel into a second Events tab. Both are already paginated elsewhere.
Q4 — Build order. This is specced against 69cd3660 and should be built after it. If you would rather ship the approval surface first, the honest version omits the documents block entirely and ships without it — not with spec_doc rendered as an unverified link.
